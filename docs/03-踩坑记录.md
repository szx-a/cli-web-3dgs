# 03 · 踩坑记录（实现全过程）

> 本文与记忆体 `cvcg` 同步。每条都写清：**现象 → 原因 → 解法 → 影响范围**。
> 目的：换台机器或换个人接手时，不用把这些坑再踩一遍。

---

## A. 环境与权限类

### A1. 工作区不可写，所有命令直接失败
- **现象**：`SetNamedSecurityInfoW failed (Win32 5): grantWrite(F:\3dgs-and-ai)` —— 连 `Get-Location` 都跑不了。
- **原因**：工作区目录缺少 `WRITE_OWNER` 权限，DSH 无法给它授予写权限；目录的权限项是继承自卷根的不完整集合。
- **解法**：用 DSH 自带的权限诊断脚本（`diagnose-windows-sandbox-acl`）为当前用户补一条完全控制项 + 重读校验。备份与回滚脚本落在 `F:\dsh-acl-recovery\`。
- **影响**：这是一切的前置；修好后 `pwsh` 才可用。

### A2. `D:\3dgs-workspace` 无法创建（沙箱只授权 F 盘）
- **现象**：`New-Item : 对路径"3dgs-workspace"的访问被拒绝`。
- **原因**：DSH 文件沙箱只允许写会话工作区 `F:\3dgs-and-ai`。
- **解法**：一次提权，在 D 盘建 `D:\3dgs-workspace`，并把 `env / workspace / tools / models / downloads`
  做成**目录链接（junction）**指向 F 盘真实目录。用户视角仍是 D 盘，写入实际落在沙箱授权区内。
  ```powershell
  New-Item -ItemType Junction -Path 'D:\3dgs-workspace\env' -Target 'F:\3dgs-and-ai\env'
  ```
- **影响**：之后所有安装/训练命令都不需要再提权。

### A3. `TEMP/TMP` 指向沙箱临时目录 → 到处 `WinError 5`
- **现象**：`ensurepip`、`get-pip.py`、`pip install -e .`、`pytest` 都报
  `PermissionError: [WinError 5] ... tmp6w3knrmn`（发生在 `shutil.rmtree` / `tempfile._resetperms` 里）。
- **原因**：沙箱临时目录 `C:\Users\admin\AppData\Local\Temp\dsh-XXXX` 里，Python 的临时目录清理会对文件做
  `chmod`（Python 3.13 在 Windows 上为删除只读文件而重置权限），这一步被沙箱拒绝。
- **解法**：把 `TEMP`/`TMP` 指到工作区内（`F:\3dgs-and-ai\env\tmp`）。
  代码层统一由 `paths.child_env()` 注入，脚本层在 `bootstrap.ps1` / `gsflow.cmd` 里设置。
- **注意**：`python -m venv` 仍然失败（venv 创建时会先 chmod 自己的临时目录），所以**建环境必须用 uv**。

### A4. `python -m venv` / `ensurepip` 不可用
- **现象**：`Error: Command '[...python.exe, -m, ensurepip...]' returned non-zero exit status 1`。
- **解法**：`uv venv <path> --python D:\python\python.exe`；pip 用 `uv pip install pip` 补进环境。
- **副作用**：uv 建的 venv 默认没有 pip，需要显式补一个（本项目已做）。

### A5. `pip install -e .`（PEP 517 构建）整条路走不通
- **现象**：`ERROR: Could not install packages due to an OSError: [Errno 13] Permission denied:
  'env\tmp\pip-build-tracker-xxx\...'`；改用 uv 也报同类错误（在 `uv-cache\builds-v0\.tmp...`）。
- **原因**：构建后端（setuptools/pep517）在临时目录里做 chmod/清理，与 A3 同源。
- **解法**：**放弃 editable install**，改为在 `site-packages` 放一个 `gsflow-dev.pth`，内容就是 `src` 路径。
  ```powershell
  Set-Content -Path 'env\venv\Lib\site-packages\gsflow-dev.pth' -Value 'F:\3dgs-and-ai\src' -Encoding ASCII
  ```
  控制台入口用 `scripts\gsflow.cmd` 代替 `gsflow.exe`。
- **影响**：`pip install -e .` 在本机永远不要用；装包一律 `uv pip install --python env\venv\Scripts\python.exe`。

### A6. `pytest` 的 `tmp_path` / `basetemp` 让整个 session 崩掉
- **现象**：测试能跑，但收尾时报 `PermissionError: os.scandir('...pytest-of-admin')`，
  接着 5 个用例全部 `ERROR`；更糟的是，清理中断会把测试临时目录的权限项**弄坏**，
  之后 `mkdir` 直接 `WinError 5`，需要提权 `icacls <dir> /reset /T` 才能恢复。
- **解法**：不用 pytest 的临时目录。`tests/test_smoke.py` 自定义 `workdir` fixture，
  目录放在 `env\pytest-tmp`；跑测试加 `-p no:cacheprovider`。
- **教训**：在这个环境下，任何“自动创建 + 自动删除临时目录”的库都要先验证。

### A7. `pwsh.exe` 不存在、脚本被执行策略拦住
- **现象**：`pwsh : 无法将"pwsh"项识别为 cmdlet`；`未对文件 bootstrap_m0.ps1 进行数字签名`。
- **原因**：本机只有 Windows PowerShell 5.1；`CurrentUser` 执行策略是 `RemoteSigned`。
- **解法**：`.cmd` 里调 `powershell.exe`；手动跑脚本加 `-ExecutionPolicy Bypass -File`。

### A8. PowerShell / curl 的 HTTPS 全部失败
- **现象**：`Invoke-WebRequest` 报 `基础连接已经关闭`；`curl.exe` 报
  `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`（错误码 000）。
- **原因**：沙箱里进程拿不到证书凭据（Schannel 凭据句柄失败）。
- **解法**：**所有下载改用 Python**（`urllib.request` 走 OpenSSL，正常）。
  已实现 `scripts/download_tools.py`（支持断点续传），需要新下载源时直接加进 `CATALOG`。

### A9. 控制台中文乱码
- **现象**：`gsflow doctor` 输出 `ϵͳ` 之类的乱码。
- **原因**：Windows PowerShell 5.1 控制台默认 GBK 代码页，Python 输出 UTF-8。
- **解法**：`.cmd` 里 `chcp 65001`；子进程环境加 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`。

## B. 硬件与 CUDA 类（本项目最关键的一条）

### B1. 文档里的 CUDA 11.8 在本机完全不可用
- **现象**：原工程文档写“CUDA Toolkit 11.8：与 3DGS 兼容性最佳”。
- **原因**：本机 GPU 是 **RTX 5060 Laptop（Blackwell，compute capability sm_120）**，
  驱动 573.22。CUDA 11.8（2022 年）不认识 sm_120，`nvcc -arch=sm_120` 直接失败；
  驱动也不接受 11.x 运行时。原版 `diff-gaussian-rasterization` 在 RTX 50 上编译失败是上游已知问题
  （[issue #1295](https://github.com/graphdeco-inria/gaussian-splatting/issues/1295)）。
- **解法**：
  - CUDA 用 **12.8.x**（与驱动 573.22 同代）或 12.9.x；
  - torch 必须 cu128+ 轮子（≥2.7 才含 sm_120 内核）；实测 `torch 2.11.0+cu128` 可用，
    `torch.cuda.get_device_capability()` 返回 `(12, 0)`，CUDA 张量运算正常；
  - 编译任何 CUDA 扩展前设 `TORCH_CUDA_ARCH_LIST=12.0`。
- **影响**：整个训练可行性；已把这条写进 `config`/文档/AGENTS。

### B2. gsplat “静默禁用”，报 `'NoneType' object has no attribute 'CameraModelType'`
- **现象**：`import gsplat` 成功，但一调用 `rasterization` 就:
  `AttributeError: 'NoneType' object has no attribute 'CameraModelType'`。
- **原因**：gsplat 的 `cuda/_backend.py` 在导入时判断 `cuda_toolkit_available()`；
  本机没有 nvcc → 它只打印一句黄字 `No CUDA toolkit found. gsplat will be disabled.`，
  然后 `_C = None`。真正的失败被这行日志掩盖了。
- **定位方法**：直接看 `gsplat/cuda/_backend.py` 的导入逻辑（不要只看报错栈）。
- **解法**：装 CUDA Toolkit（提供 nvcc）。安装脚本 `scripts/install_cuda.ps1` 已写成
  “只装 nvcc/头文件/库 + VS 集成，不动显卡驱动”，避免黑屏风险。
- **验证**：`python -c "from gsplat.cuda._backend import _C; print('ok')"`，
  第一次会现场编译内核（3~10 分钟）。

### B3. 显存只有 8GB（实际可用 ~6.5GB）
- **现象**：桌面应用（浏览器/微信/Steam）已占用 1.2~1.5GB。
- **解法（已内建）**：
  - `train.cap_max` 限制高斯数量（默认 150 万，可按场景下调）；
  - 渐进分辨率（前 15% 迭代半分辨率热身）；
  - 训练 OOM 时自动按 `1600→1400→1200→1000→800→600` 降档重试一次；
  - 训练前建议关掉浏览器等占显存程序。
- **经验值**：150~250 张图、长边 1400~1600、30k 迭代，8GB 可以跑完。

### B4. 内存只有 15.2GB（可用一度只剩 3.9GB）
- **注意**：COLMAP 全局匹配（exhaustive）在大数据集上吃内存，超过 ~500 张图建议用
  `sequential` 或 `vocab_tree`；同时避免和训练并发。

## C. 工具链类

### C1. COLMAP 官方 Windows 包给的是 `COLMAP.bat`，直接调用会失败
- **现象**：把 `COLMAP.bat` 当 exe 传给 `subprocess` 会报错或找不到 DLL。
- **原因**：bat 内部依赖同目录的 `bin\*.dll` 与插件，必须在自身目录下启动。
- **解法**：`tools/runner.py` 统一适配——`.bat/.cmd` 一律 `cmd.exe /c <bat> args`，并把 `cwd` 固定到脚本目录。
- **附带**：`COLMAP.bat` 不认 `-version`，版本探测要用 `colmap help`（已做 `VERSION_ARGS` 表）。

### C2. zip 解压后的目录层级不确定
- **现象**：FFmpeg 解压成 `tools/ffmpeg/bin/ffmpeg.exe`，COLMAP 解压成 `tools/colmap/bin/colmap.exe` + 顶层 bat。
- **解法**：`download_tools.py` 里 `flatten_single_dir()` 拍平多余层级；
  `locate.py` 的 `CANDIDATES` 同时列出 `bin/` 与顶层两种布局。

### C3. 网速极慢（实测 0.15~0.4 MB/s）
- **影响**：torch cu128 下载耗时 **47 分钟**；CUDA Toolkit 3.3GB 约需 3~5 小时。
- **解法**：
  - 所有大文件下载都实现**断点续传**（`download_resumable`，`.part` + `Range`，最多重试 200 次）；
  - `scripts/speedtest.py` 可测各源速度；
  - 若用户有更快通道（浏览器下载器/代理/离线包），把文件丢进 `downloads/` 同名即可被识别跳过。

### C4. `huggingface.co` 连通性不稳定
- **现象**：同一台机器上，socket+TLS 测试有时超时、有时成功；首次测试失败、稍后 `doctor` 显示可达。
- **解法**：配置里提供 `hf_endpoint`（推荐 `https://hf-mirror.com`）与 `http_proxy`/`https_proxy`；
  下载权重前先跑设置页的「测试 HuggingFace 连通性」。

### C5. COLMAP 3.12 开启 loop_detection 会直接崩溃（无 vocabulary tree）
- **现象**：`sequential_matcher` 在 `Generating image pairs with vocabulary tree...`
  处原生崩溃，退出码 `3221226505`（0xC0000409 STATUS_STACK_BUFFER_OVERRUN）。
- **定位过程**：先用 `--SiftMatching.use_gpu 0` 复现（排除显存/GPU），再单独加回
  `--SequentialMatching.loop_detection 1` → 必崩。即“开了闭环检测但没有 vocab tree 文件”。
- **解法**：**默认关闭闭环检测**；只有 `colmap.vocab_tree_path` 指向真实存在的
  vocab tree 文件时才启用（见 `stages/colmap.py`）。需要官方 vocab tree 时单独下载再填路径。
- **注意**：这个崩溃不带任何 Python 异常，`run_tool` 只能拿到退出码，因此错误信息里
  专门提示“看起来是原生崩溃”并列出三个高频原因。

### C6. COLMAP 选项名跨版本变化，写死参数会直接失败
- **现象**：`Failed to parse options - unrecognised option '--SequentialMatching.guided_matching'`。
- **原因**：COLMAP 3.12 把 guided matching 归到 `--SiftMatching.guided_matching`，
  早期版本则在 matcher 自己的命名空间下。
- **解法**：`tools/runner.py` 增加**选项能力探测**：抓 `colmap <subcommand> --help` 里的
  选项全集并缓存，执行前过滤掉当前版本不认识的“选项+取值”，同时在日志里 warn 出来。
  这样跨版本都能跑，而不是一升级就炸。

### C7. 阶段元数据文件被 COLMAP 当成图像
- **现象**：`E feature_extraction.cc:266] frames.json BITMAP_ERROR: Failed to read the image file format.`
- **原因**：COLMAP 会枚举 `--image_path` 下的所有文件，不做扩展名白名单。
- **解法**：元数据改用下划线前缀（`_frames.json`）并尽量少放；同时所有读目录的地方
  都按图像扩展名过滤（`IMAGE_EXT`）。

## C+. 训练数据准备类（在合成数据实测中发现）

### C8. `image_undistorter` 按“模型里的图像名”找文件，名字对不上就静默跳过
- **现象**：`02_images_clean` 有 36 张图，undistorter 日志只写
  `Undistorting image [1/5]`，输出目录只有 5 张，训练阶段随后报“找不到稀疏模型/图像”。
- **原因**：undistorter 遍历的是重建里的 `image.name`，到 `--image_path` 下按该名字找文件；
  我们早期把图像重命名成 `00000.jpg...` 再传进去，名字全对不上，于是只处理了恰好同名的那几张。
- **解法**：`prepare_undistorted()` 先 `read_model()` 取出**已注册图像名**，
  只复制这些文件、**保持原名**，并顺带报告“多少张找不到”（`missing`）。
  这条同时也解释了为什么训练必须有与 COLMAP 一致的原始图目录。

### C9. COLMAP 3.12 的去畸变输出布局变了：`sparse/` 而不是 `sparse/0/`
- **现象**：训练阶段报“找不到 COLMAP 稀疏模型：04_train\data\sparse\0”，
  但 `04_train\data\sparse\cameras.bin` 确实存在。
- **原因**：3.12 的 `image_undistorter` 把 `cameras.bin / images.bin / points3D.bin`
  直接写在 `sparse\` 下（还多了 rigs.bin / frames.bin）。
- **解法**：新增 `find_model_dir()`，依次尝试 `sparse/0`、`sparse`、`sparse/*` 三种布局；
  训练阶段的“数据是否就绪”判断也改用它。

### C10. `torch.from_numpy` 读到只读数组会告警（并可能引发未定义行为）
- **现象**：`UserWarning: The given NumPy array is not writable ...`。
- **解法**：`np.asarray(im, dtype=np.uint8).copy()` 后再转 tensor。

### C11. 分割失败时写 1x1 空掩码 → 下游拿到全黑图（静默废帧）
- **现象**：某张图没检出前景时，早期实现写了一个 `1x1` 的空掩码 PNG，
  清理图则是全黑；COLMAP 会把它当一张全黑照片吃进去（等价于丢帧但没有任何报错）。
- **解法**：新增 `mask.on_failure` 策略：
  - `keep`（默认）→ **原图直通**，清理图仍是原图，manifest 里单独记 `fallback_kept_original`；
  - `skip` → 明确丢弃该帧。
  并且全部失败时给出"已回退"的明确提示，而不是静默产出垃圾。

### C12. 模型权重没装时，无法验证 mask 阶段 → 增加零依赖兜底后端
- **背景**：FastSAM/rembg 需要下载权重，SAM2/SAM3 还需要 HF 授权；在下载受限的机器上
  mask 阶段完全无法验证。
- **解法**：实现 `classical` 后端（背景中位数估计 + RGB/色度距离 + Otsu 自动阈值 + 开运算），
  纯 numpy/PIL、无需任何权重。合成数据实测 **IoU 0.93~0.98**，足够用于静置物体与均匀背景。
- **附加收益**：`tests/test_mask_stage.py` 现在能在无 GPU、无权重、无网络的情况下
  回归整个 mask 阶段契约（掩码/黑背景/overlay/manifest/回退策略）。

### C13.【实测踩到】COLMAP 的掩码文件名规则是 `图片全名.png`，不是 `stem.png`
- **现象**：`E feature_extraction.cc:266] 00033.jpg MASK_ERROR: Failed to read the mask file.`
  —— 36 张图全部报错（后来只剩 2 张，见 C14）。
- **原因**：`--ImageReader.mask_path` 下，COLMAP 找的是 `<image_name>.png`，
  即 `00033.jpg` → **`00033.jpg.png`**；而我们内部习惯用 `00033.png`。
- **解法**：`imageops.mask_paths_for()/find_mask_path()` 统一两种约定；
  写入时**两种都产出**，读取时**两种都尝试**。并加了回归测试防止再退化。

### C14. 回退帧（未检出前景）漏写 COLMAP 命名掩码
- **现象**：修完 C13 后仍有 2 张报 MASK_ERROR，正好等于 manifest 里的
  `fallback_kept_original` 数量。
- **原因**：原图直通分支只写了 `{stem}.png`，漏了 `{image_name}.png`。
- **解法**：回退分支同样写两种命名。

### C15. 加了 mask 之后 `Check failed: max_num_matches > 0` 崩溃
- **现象**：`[sift.cc:89] Check failed: max_num_matches > 0 (0 vs. 0)`，退出码 0xC0000409。
- **原因**：COLMAP 的 `SiftMatching.max_num_matches` 在未显式指定、且部分选项组合
  （如 guided_matching 被版本过滤掉）下会取到 0，触发断言。
- **解法**：匹配命令显式传 `--SiftMatching.max_num_matches 32768`（可用
  `colmap.max_num_matches` 配置），不再依赖默认值。

## D. Windows 脚本与第三方库目录

### D1.【严重】`.ps1` 没有 BOM + 含中文 → PowerShell 5.1 解出满屏语法错误
- **现象**：跑 `install_cuda.ps1` 报
  `表达式或语句中包含意外的标记"寮€濮嬮潤榛樺畨瑁?.."`、`缺少右")"`、`赋值表达式无效`，
  但用 `read` 工具看文件内容完全正常。
- **原因**：Windows PowerShell 5.1 对**没有 BOM** 的 `.ps1` 按系统 ANSI（中文机器是 GBK）解码。
  我们写的是 UTF-8，中文字节被误解码后正好吞掉了字符串的结束引号，于是语法崩塌。
  （UTF-8 的无 BOM 依赖是 v7+ 的行为，5.1 不认。）
- **解法**：`.ps1` 一律写成 **纯 ASCII 内容 + UTF-8 BOM + CRLF**。
  校验两件事：
  ```powershell
  # 1) 前 3 字节应为 EF BB BF（UTF-8 BOM）
  [System.IO.File]::ReadAllBytes($f)[0..2] | ForEach-Object { $_.ToString('X2') }
  # 2) 语法检查（$errors 为空即通过）
  [System.Management.Automation.Language.Parser]::ParseFile($f, [ref]$null, [ref]$errors)
  ```
  已修：`scripts\bootstrap.ps1`、`scripts\install_cuda.ps1`（均 BOM + 语法 OK）。
- **同类教训**：任何“被外部程序按 ANSI 解码”的文本都要小心——包括用 PowerShell 的
  `Get-Content/Set-Content` 去改含中文的 UTF-8 源码（见 B 组第 8 条，把 `frames.py` 写坏过）。

### D2. ultralytics 想写 `AppData\Roaming` → `WinError 5`
- **现象**：`import ultralytics` 报 `PermissionError: [WinError 5] 拒绝访问。: 'C:\Users\admin\AppData\Roaming\Ultralytics'`。
- **原因**：ultralytics 首次导入会在用户 Roaming 目录建配置。沙箱只授权工作区。
- **解法**：**导入之前**设置 `YOLO_CONFIG_DIR` 到工作区（`paths.runtime_env()` 统一注入，
  `scripts\gsflow.cmd` 也设了）。同理 matplotlib 需要 `MPLCONFIGDIR`。

- **现象**：管理员运行 `install_cuda.ps1` 后，安装器返回 `-522190823`（= `0xE0E00019`），
  D 盘没有生成 CUDA 目录，脚本预期的 `logs\cuda_install.log` 也没生成。
- **已验证的部分**（排除掉的可能性）：
  - 安装包完好：3213.2 MB，`ProductName = NVIDIA Package Launcher`，**数字签名 Valid（NVIDIA Corporation）**；
  - 组件名合法：NVIDIA 自己的 setup 日志里有
    `Found 66 sub-package config files - 0 excluded - 66 selected unique`，
    并且逐个加载了 `nvcc_12.8` / `cudart_12.8` / `CUDADevelopment_12.8` 等包；
  - 安装器确实启动过：`%LOCALAPPDATA%\Temp\NvidiaLogging\Log.4828setup.exe.log`（177 KB）。
- **关键观察**：那份 NVI2 日志只覆盖“加载清单 → 缓存安装包 → 卸载扩展 DLL”这一段（约 2.3 秒），

  并给出三条降级路径（显式组件名 / 交互式只勾 Development / 干脆不装）。
- **重要结论**：**除训练阶段外，其余阶段都不需要 CUDA**。
  测过：frames / mask / colmap / export / metrics 全部可在无 nvcc 环境下工作。

### F4.【关键突破】不需要管理员权限的"便携 CUDA"
- **思路**：官方 CUDA 安装包（`cuda_12.8.1_572.61_windows.exe`）本质是 **7z 自解压包**，
  而 Windows 10+ 自带 `bsdtar`（`tar.exe`）**能读 7z**。于是：
  ```bat
  tar -xf downloads\cuda_12.8.1_572.61_windows.exe -C env\cuda_pkg cuda_nvcc cuda_cudart cuda_cccl
  ```
  只取三个子包，拼成 `tools\cuda`：**358 MB，含 nvcc 12.8.93，全程零管理员权限**。
  - `cuda_nvcc/nvcc/` → `tools\cuda\`（bin / nvvm / include）
  - `cuda_cudart/cudart/include` + `lib\x64` + `bin` → 对应标准位置
  - `cuda_cccl/thrust/include` → `tools\cuda\include`
  - 另把 `tools\cuda\bin\crt\*` 复制到 `include\crt\`
  已封装为 `scripts\build_portable_cuda.cmd`，并加了 `paths.find_portable_cuda()` 自动识别。
- **意义**：`0xE0E00019` 那类安装器问题可以完全绕开；把 3.2GB 安装包变成 358MB 可移植工具链。

### F5. nvcc 还需要 `cl.exe`（vcvars 环境）
- **现象**：便携 CUDA 就绪后 `nvcc` 报 `nvcc fatal : Cannot find compiler 'cl.exe' in PATH`。
- **原因**：nvcc 不是独立编译器，主机端要调用 MSVC 的 cl.exe。
- **解法**：`scripts\gsflow_gpu.cmd` 先 `call vcvars64.bat`（自动在 VS2022 BuildTools /
  VS2022 / VS2026 之间找），再设置 `CUDA_HOME` / `TORCH_CUDA_ARCH_LIST=12.0` 并执行 gsflow。
- **踩坑**：`.cmd` 里**不能用带括号的 if 块**——`C:\Program Files (x86)\...` 里的 `(x86)`
  会让 cmd.exe 把它当成代码块结束符，报
  `\Microsoft was unexpected at this time.`。必须改成 `if ... goto label` 的写法。
- **另一个坑**：`.cmd` 文件**不能带 UTF-8 BOM**，cmd.exe 会把 BOM 当命令的一部分。

### F6. 【关键】中文 Windows 下 torch 解码编译器的输出会崩
- **现象**：gsplat 编译内核时报
  ```
  File "torch/utils/cpp_extension.py", line 502, in get_compiler_abi_compatibility_and_version
    match = re.search(r'(\d+)\.(\d+)\.(\d+)', compiler_info.decode(*SUBPROCESS_DECODE_ARGS).strip())
  UnicodeDecodeError: 'cp1' codec can't decode bytes in position 0--1: No mapping for the Unicode character exists
  ```
  最终表现为 `_C = None` + `'NoneType' object has no attribute 'CameraModelType'`。
- **原因**：`torch.utils.cpp_extension.SUBPROCESS_DECODE_ARGS` 默认是 `('oem',)`；
  中文 Windows 下 cl.exe 输出 UTF-8（控制台代码页 65001），用 OEM 码页解码必然失败。
  这个解码错误发生在 torch 内部，只在 gsplat 的 VERBOSE 输出里才看得到，非常隐蔽。
- **解法**：在 `paths.apply_runtime_env()` 里把
  `torch.utils.cpp_extension.SUBPROCESS_DECODE_ARGS` 改成 `('utf-8',)`
  （CLI 与 GUI 入口都会自动应用）。可用
  `env\venv\Scripts\python.exe -c "import torch.utils.cpp_extension as ce; print(ce.SUBPROCESS_DECODE_ARGS)"`
  验证。
- **附带**：`.cmd` 里同时设 `VSLANG=1033` 让 MSVC 输出英文，减少中文字节带来的概率性失败。

### F8.【关键】ninja 在本环境"干完活但不退出" → torch 永久卡死
- **现象**：gsplat 编译内核时 `ninja` 进程 CPU=0、构建目录只有 build.ninja、日志为空、永不结束。
- **定位**：用最小 build.ninja 测试——**任务确实完成了**（`out.txt` 已生成），
  但 ninja 进程不退出；官方版与 MinGW 版两个 ninja 都一样。
  而 `torch.utils.cpp_extension._run_ninja_build` 是**同步等待 ninja 退出**的，于是永远卡住。
  （另有一个次要原因：上一次失败留下的 `lock` / `.ninja_lock` 会让 ninja 直接挂起。）
- **解法**：**绕过 ninja**——`src/gsflow/build.py` 直接解析 torch 生成的 `build.ninja`，
  自己调用 cl.exe / nvcc.exe / link.exe；`paths.apply_runtime_env()` 检测到 ninja
  不可用（20 秒探针）时把 `_run_ninja_build` 换成它。可用 `GSFLOW_FORCE_NINJA=1` 强制回退。
- **附带修掉的 4 个坑**（都在 build.py 里）：
  1. cl.exe 命令里带着 GCC 风格参数（`-O3 -Wno-attributes`）→ `D8021 无效的数值参数`，
     整批 .cpp 编译失败 → 做参数归一化（`-O3`→`/O2`，`-W*` 剔除）。
  2. 链接命令里 `C$:\Program Files\...` —— ninja 的 `$:` 转义没解开 → 链接器报
     "filename, directory name, or volume label syntax is incorrect" → 展开后再解一次转义。
  3. `cub/cub.cuh` 间接引入 Windows `rpcndr.h` 的 `#define small char`，
     把 torch 头里 `StreamSegmentSize(..., bool small, ...)` 的参数名替换成 `char`
     → `invalid combination of type specifiers`。`-Xcompiler /Usmall` 与 `-Dsmall=` 都太晚/无效，
     最终用**头文件遮蔽**：在 include 路径最前面放一个同路径头，先 undef 再 include 真正的头。
  4. `/showIncludes` 产生的上万行 "注意: 包含文件" 灌爆日志 → 编译时剔除该参数。

### F9.【关键】相机位姿翻转写错 → alpha 恒为 0、密度控制完全不触发
- **现象**：训练能跑完，但 `alpha 和 = 0`、`means.grad.abs().sum() = 0`，
  高斯数量从 427 到结束都不变，PSNR 为 0（只有不透明度/颜色被优化，loss 会缓慢下降，很具迷惑性）。
- **原因**：`load_colmap_data` 里照抄 gsplat 示例写了 `c2w[0:3, 1:3] *= -1`（y、z 都翻），
  这在本流程的数据上把**所有点放到了相机背后**（相机空间 z 全为负）。
- **定位方法**：`scripts/probe_pose_convention.py` 扫 4 种翻转组合，统计"相机前方点数 / alpha 和 / 位置梯度"：
  ```
  y*+1 z*+1   alpha 和=7249.5   前方点 427/427   梯度 7.9e-02   ← 正确
  y*+1 z*-1   alpha 和=0.0      前方点 0/427     梯度 0.0
  ```
- **解法**：只翻 y（`c2w[0:3, 1] *= -1`）。
- **教训**：训练"能跑完"不等于"在工作"。必须断言 alpha 非零与梯度非零，
  所以在 `train()` 里保留了 step 1 的探针（alpha 和 / 可见像素 / 梯度）。

### F10. 密度控制的三处逻辑错误（修完才开始真正加密）
1. **阈值量纲**：官方 0.0002 是对位置梯度**取平均**的量纲；我们用的是每个高斯的梯度范数
   （实测均值 ~2e-4、最大 ~1.2e-2），直接用会让加密几乎不发生 → 校准为 `1.5e-4` 并可配置。
2. **条件互斥**：早期把"梯度过阈"和"尺度过小"做**与**，实测两组点交集为 0
   （梯度过阈组尺度均值 0.45，尺度过小组梯度不够）→ 改为**只按梯度选候选**，
   在加密时对**小尺度克隆、大尺度分裂**（官方策略）。
3. **顺序 + 裁剪规则**：早期"先裁剪后复制"，而两个掩码都按裁剪前的张量算，索引立刻失效；
   而且把"尺度过大"也当裁剪条件，会立刻删掉刚加密出来的点
   （实测 427 → 加密 46 → 又被裁 78 → 只剩 395，做了负功）。
   现在：**先加密（掩码最先用）→ 再按不透明度裁剪**。

### G6.【已修复·决定训练成败】相机位姿**不需要任何轴翻转** + 初始尺度必须用最近邻
这两个问题合起来让 PSNR 长期卡在 13~14 dB（现在的水平是 34.79 dB，**留出视图**）。

**(1) 相机位姿不翻转**
- 我先后用过 `c2w[0:3, 1:3] *= -1`（照抄 gsplat 示例）和后来"修"成的
  `c2w[0:3, 1] *= -1`，**两者都是多余的**。
- 官方 `examples/datasets/colmap.py` 的做法：
  ```python
  w2c = [[R|t],[0|1]]          # COLMAP: world -> camera
  camtoworlds = np.linalg.inv(w2c)   # 直接求逆，不翻任何轴
  ```
  而本项目 `colmap_io.Image.cam_to_world()` 返回 `(R.T, -R.T @ t)`，
  正是 `inv([[R|t],[0|1]])` 的解析解 —— **完全等价**，所以额外翻转都是错的。

**(2) 初始尺度必须用最近邻距离，不能用"到质心距离"**
- 官方 `create_from_pcd`：`dist2 = distCUDA2(points)`（到最近邻的平方距离均值），
  `scales = log(sqrt(dist2))`。
- 我原来用"到点云质心的距离 × 0.5"。对一块平面，质心到各点距离≈平面半径（本例 ~1.0），
  于是初始高斯有半个场景那么大 → 整幅图被少数巨大高斯糊住 → 渲染是一片带颜色的雾。
- 改成最近邻后初始尺度 1.0 → **0.031**（≈ 官方 `scene_scale*0.01` 量级），
  PSNR 立刻从 18.9 跳到 **33.75 dB**。
- 实现见 `_init_scales_nn()`（分块 cdist，避免大场景构造 N×N 矩阵）。

**(3) 怎么定位的（方法论，值得记住）**
- **无效判据**："把稀疏点当小高斯渲染再算 PSNR"。
  1846 个点渲染成小圆点覆盖不到整张图，两种位姿约定都只有 ~10 dB，没有判别力。
- **有效判据**：投影 + 纹理一致性（新增 `scripts/verify_pose_projection.py`）。
  把 COLMAP 稀疏点投影成像素，再看该处图像梯度：
  ```
  不翻转   点处梯度 21.17 / 全图 2.62 = 8.07x   ← 正确（与官方一致）
  翻 y     点处梯度 12.40 / 全图 2.62 = 4.73x
  ```
- **教训**：判断几何问题要找**能在几何上直接证伪**的判据（投影是否落在特征上），
  而不是拿间接指标（PSNR）硬试。

### G7.【已修复】不透明度重置必须配套"重置后重新致密化"
- 官方每 3000 步把不透明度压回 0.01，**紧接着会对所有高斯做一次 densify** 补回容量。
- 我只实现了"压回 0.1"、漏了配套的补回步骤，等于每次重置都把模型打掉一大半。
- 实测（同一份数据，只改这一个开关）：
  | 配置 | step 6000 PSNR | 最终 |
  |---|---|---|
  | 重置开 + 密度控制开 | 21.47 | 21.47 |
  | 重置开 + 密度控制关 | 19.02 | 19.02 |
  | **重置关** + 密度控制关 | **36.28** | **36.44**（稳定上升） |
- 因此本项目默认 `opacity_reset_interval = 0`（关闭）。
  **若要开启，必须先实现"重置后致密化"**，否则不要打开。

### G8.【已修复】加密阈值不要做"分位数自适应"
- 官方用的是**固定绝对阈值**（`grow_grad2d = 0.0002`，作用在按视图累积的 2D 屏幕梯度上）。
- 我一度改成"取梯度范数的 (1-q) 分位作阈值"，结果梯度一衰减阈值就跟着降 →
  **无限膨胀**（6000 步涨到 6 万高斯，PSNR 从 33.75 掉到 21.47）。
- 关键认识：**梯度随优化自然衰减，本身就是"该停止加密"的信号**，
  不需要（也不应该）人为跟随。现已改回固定阈值（`densify_grad_threshold = 2e-4`），
  `densify_quantile` 默认 0（仅保留作实验开关）。

### G9.【已修复】PLY 的表示约定：scale 是 log 值、opacity 是 logit
- 官方 inria PLY 约定：`scale_* = log(真实尺度)`、`opacity = logit(概率)`。
- 我的 `save_ply` 收到的是已 `exp` 的真实尺度和已 `sigmoid` 的概率，却原样写入，
  于是导出阶段 `_read_ply` 又 exp 一次 → 尺度放大 **200 倍**（0.005 → 1.005），
  渲染成一片糊住画面的灰雾。
- **注意影响面**：训练内的诊断渲染直接用内存参数、不经过 PLY 往返，
  所以 PSNR 34.79 dB 那个结果**是可信的**；受影响的只有导出产物
  （GLB / 预览图 / 查看器）。
- 已修：写盘时 `log(clamp(scales))` 与 `logit(clamp(opacities))`，
  与官方 PLY 对齐，SuperSplat / three.js 也能正确读。

### G10. 预览图要用真实渲染，不要用散点图
- 原来 `_render_previews` 用 matplotlib `ax.scatter` 画高斯**中心点**，
  得到的是一团点云 —— **一个 PSNR 35dB 的好模型和一堆乱点长得一样**，
  完全无法反映重建质量（我因此误判了好几轮）。
- 现改为 gsplat 无头真实渲染：相机优先取**训练时的真实位姿**
  （自己估的环绕相机很容易取景失当，实测渲成一片纯背景色），
  有真值图时把"渲染 | 真值"并排拼一张，可直接对照。
- gsplat/CUDA 不可用时自动退回散点图，保证导出阶段仍可独立运行。

### G11.【已修复】COLMAP 度量读错了列
- `images.txt` 每行是 `IMAGE_ID QW QX QY QZ TX TY TZ CAMERA_ID NAME`，
  第 8 个字段（索引 7）是 **TY（相机平移分量）**，不是重投影误差！
  早期代码读的正是 `parts[7]` → "平均重投影误差"实际是相机 TY 的均值
  （实测 99.987px，看着像标定崩了，其实重建误差只有 0.8px），
  还会误触发 "> 2.0px 标定可能不稳定" 的告警。
- 真正的逐点重投影误差在 `points3D.txt` **第 8 列**（`POINT3D_ID X Y Z R G B ERROR TRACK[]`）。
- 同时修注册率统计：原来 `len(parts) >= 10` 会把每张图的 POINTS2D 行也算上
  （16 张报成 32 张），改为只统计位姿行（第 10 列是图片文件名）。
- 修复后：注册 36/36、平均重投影误差 **1.08px**，与 COLMAP 自报的
  "Number of images: 36" 一致。

### G12.【已修复】合成基准数据本身是坏的
- 平面角点是 `(±hs, ±hs, 0)`（位于 z=0、法线朝 +z），而相机轨迹是
  `(r·cosθ, 小高度, r·sinθ)` —— θ=0 时相机在 `(r, 0.15, 0)`，
  视线几乎与平面**平行**，平面被侧视成一条线；相机高度只有 0.15（仰角 2.4°），
  基线也几乎退化。渲染出来是一张几乎全黑的图。
  后果：SIFT 无特征，36 张只注册 14 张，重建无从谈起。
- **还有第二个坑**：`render_view` 用单应 + `PIL.Image.transform`。
  单应矩阵本身算对了（`H @ src` 精确等于目标图像坐标），
  但 PIL 的 fillcolor/逆映射/越界约定把整块四边形填成黑色，**且不报任何错**。
- 修法：相机改为**绕平面法线（+z）环绕**并向 +z 侧抬高，始终正对平面；
  渲染改成**逐像素光线投射**（对每个像素发射线求与平面交点再采样纹理），
  从第一性原理出发、完全可控，不依赖图像库的隐式约定。
- 效果：注册率 14/36 → **36/36**，图像成为铺满纹理的平面。

> 这一批（G6~G12）的共同教训：**"配置/约定类"的错误几乎都是静默的**。
> 它们不报错、不崩溃，只是让结果变差，而且很容易被误判成"算法不行"。
> 对付它们的办法是**找一个能在几何上直接证伪的判据**，
> 以及**对齐官方实现并逐条核对它做了哪些约束**。

### F13. 密度控制必须照抄官方 gsplat 的"参数字典 + 迁移优化器状态"
这一处我前后错了 4 次，每次都表现为不同的报错或"静默不生效"。
**结论：不要自己发明参数扩缩容的写法，直接对齐社区成熟实现。**

官方的做法（`gsplat/strategy/ops.py:_update_param_with_optimizer` + `duplicate/split/remove`）：

```python
def param_fn(name, p):
    return torch.nn.Parameter(torch.cat([p, p[sel]]), requires_grad=p.requires_grad)

def optimizer_fn(key, v):          # Adam 的 exp_avg / exp_avg_sq 按行拼接，新增补 0
    return torch.cat([v, torch.zeros((len(sel), *v.shape[1:]), device=v.device)])

_update_param_with_optimizer(param_fn, optimizer_fn, params, optimizers)
```

即：**替换 Parameter 对象 + 迁移 optimizer.state + optimizer.param_groups[i]["params"] = [new_param]**。

我踩过的四种错法：

| # | 错法 | 现象 |
|---|---|---|
| 1 | 改 `p.data` + 重建优化器 | `Function UnsqueezeBackward0 returned an invalid gradient ... got [N_new,16,3] but expected [N_old,16,3]` |
| 2 | 把密度控制放在 `forward` 之前 | 用的是上一步梯度，判据落后一步；顺序上更脆弱 |
| 3 | 把密度控制放在 `zero_grad` **之后**却仍读 `means.grad` | `grad` 恒为 None → **一次都不加密**（高斯数从头到尾 427） |
| 4 | `copy_` 原地裁剪（重叠索引） | `The size of tensor a (481) must match tensor b (478)` |

最终正确形态（与官方 `simple_trainer.py` 一致）：

```
forward → loss.backward()
        → 缓存 grad_norm（关键：zero_grad 之后就没了）
        → optimizer.step() → optimizer.zero_grad(set_to_none=True)
        → strategy.step_post_backward()   # 我们的 densify_and_prune
```

补充：官方用的是策略自己累积的 `grad2d` 统计量（`state["grad2d"] += grads.norm(...)`），
天然不受 `zero_grad` 影响；我们为省事改成"backward 后立刻缓存范数"，效果等价。

**修好后的实测（合成数据，813x813，15000 迭代）**：
- 427 个初始稀疏点从 step 500 开始持续加密，step 15000 达到 **557,059** 个高斯，
  之后按 `densify_until` 设计停止加密；
- loss 0.2612 → **0.0187**，训练全程无报错；
- 观察：在 7 视图的合成场景上**膨胀过猛**（55 万高斯对这么小的场景明显过多）。
  官方靠 `cap_max` 与周期性 `reset_opacity` 抑制膨胀，我们已把
  `train.cap_max` 默认从 150 万下调到 **60 万**。真实数据集应重新校准这个值。
- 完整 30k 迭代在 8GB 卡上耗时约 **90 分钟**（813x813、7 视图、55 万高斯）。

**建议**：新建训练后端时，优先考虑**直接调用 `gsplat.strategy.DefaultStrategy`**
（它把 initialize_state / step_pre_backward / step_post_backward / check_sanity 都封装好了），
而不是自己实现密度控制。本项目保留自研实现是为了不绑定 gsplat 内部 API，
但代价就是上面这 4 个坑——这是一次很值的教训。

## G. 训练算法与架构复盘

### G1.【架构级复盘·用户点出的本质】"参数变了，优化器不会自己跟上"
> 这一节是用户点出来的，比我自己总结的"4 种错法"更接近本质。

**现象层**：密度控制改了参数形状后，训练要么报
`... returned an invalid gradient ... expected shape compatible with [N_old]`，
要么静默不加密，要么张量尺寸对不上。

**本质层**：PyTorch 里**优化器与参数是"显式绑定"关系**，不是"自动跟随"：

| 对象 | 绑定方式 | 参数被替换后会怎样 |
|---|---|---|
| `optimizer.param_groups[i]["params"]` | 存的是 `Parameter` 的**对象引用** | 仍指向旧对象 → 更新的是已不参与前向的张量 |
| `optimizer.state[param]` | **以 Parameter 对象为字典 key** | 新参数查不到 state → Adam 动量/二阶矩**静默丢失**（不报错） |
| autograd 图 | 节点持有前向时用到的**张量** | 形状变了但图没重建 → backward 形状校验失败 |

所以社区实现（gsplat `strategy/ops.py`）必须手写 `_update_param_with_optimizer`：
**新建 Parameter 对象 + 把 state 按同样规则变换后挂到新对象 + 改写 param_groups**。
这不是技巧，而是这套 API 的必然要求。

**我犯的错一句话概括**：我按"自动跟踪"的直觉写（改 `p.data`、重建优化器、手动清 grad），
而这套 API 是"显式绑定 + 显式迁移"的语义 —— 方向错了，怎么试都不对。

**连带第二个坑**：判据与生命周期不同步。官方顺序是
`optimizer.step() → zero_grad(set_to_none=True) → 密度控制`，
而 `zero_grad` 之后 `means.grad` 就是 `None`。
官方策略因此**自己累积**统计量（`state["grad2d"] += grads.norm(...)`），
我一开始直接读 `means.grad` → 恒为 `None` → 一次都不加密。
最终改为"backward 之后立刻缓存 grad_norm"，效果等价。

**方法论教训**：
1. 陌生领域不要逐点试参数。先找**成熟实现的对应代码段**，对齐它的调用顺序与不变量，
   再回头比对差异。
2. 本次弯路代价很大（用户陪看 7 小时，我试了 4 轮才转向查资料）。
   本机 `raw.githubusercontent.com` 不通，但 `cdn.jsdelivr.net` 可用：
   `https://cdn.jsdelivr.net/gh/nerfstudio-project/gsplat@main/gsplat/strategy/ops.py`，
   用 Python `urllib` 下载（`web_fetch` 会因 content-type 被拒）。
3. 对"参数会变形状"的训练循环，**默认假设优化器不会自动跟随**：
   要么显式迁移，要么直接用官方策略类
   （`gsplat.strategy.DefaultStrategy` 已封装 initialize_state /
   step_pre_backward / step_post_backward / check_sanity）。

### G3.【已修复】ctx.cfg 的配置回退写错 → config.toml 的 [train] 段从未生效
- **现象**：`--set train.iterations=800` 完全不起作用，训练照样跑 30000 步；不报任何错。
- **原因**：两处叠加。
  1. `StageContext.cfg()` 的回退是 `settings.get(key)`，而 config.toml 是**嵌套**的
     （`[train] iterations` → 点路径 `train.iterations`），
     于是阶段里的 `ctx.cfg("iterations", 30000)` **永远取不到配置**，静默用默认值。
  2. 顺带发现：整个 `[train]` 段（迭代数、分辨率、密度控制参数）都是这个情况，
     也就是说**配置文件里的训练参数从来没被读过**。
- **修法**：裸键先拼当前阶段成点路径再回退（`train.iterations`），点路径写法仍直接生效；
  新增 `_MISSING` 哨兵以区分"键不存在"与"值为 None"。
- **验证**：`--set train.iterations=800` → 日志 `迭代 800`，800 步精确结束；
  无 `--set` 时能从 config.toml 读到 30000。
- **教训**：**"配置项不生效"比"配置项报错"危险得多**。
  凡是"默认值恰好合理"的静默回退，都可能在很长时间里不被发现。
  新增配置项时应顺手加一条"改它 → 行为确实变化"的验证。

### G4.【已修复·发散根因】密度控制漏了官方的"尺度裁剪"
- **量化证据**（修复前）：
  | 迭代 | 高斯数 | log尺度 max | 坐标范围 |
  |---|---|---|---|
  | 5000 | 37,158 | 41 | 125 |
  | 15000 | 557,059 | 332 | 215 |
  | 30000 | 557,059 | **739**（exp 溢出） | 215 |
  相机环绕半径仅约 3.6，坐标范围却到 215 → 高斯全飞出视锥，预览只剩原点附近一小撮。
- **根因**：官方 `DefaultStrategy._prune_gs` 有**两条**裁剪，我只实现了第一条：
  ```python
  is_prune   = sigmoid(opacities) < prune_opa                        # 0.005，已实现
  if step > reset_every:
      is_too_big = exp(scales).max(-1) > prune_scale3d * scene_scale  # 0.1，漏了
      is_prune |= is_too_big
  ```
  缺第二条 → 尺度无上界 → 分裂时 `offset = randn * 2*exp(scales)` 跟着爆炸。
- **同时纠正的第二个错误**：分裂/克隆的分界我原来用"当前尺度中位数"作参照，
  而每次分裂又把尺度除以 1.6 → 中位数下降 → 阈值自增强 → 无界分裂。
  官方用的是**绝对阈值** `grow_scale3d * scene_scale`（0.01），
  其中 `scene_scale` 由相机位置**一次性**估出。
- **修法**（全部对齐官方语义）：
  - `scene_scale` = 相机中心到其均值的平均距离（官方 `initialize_state` 同款）；
  - `grow_scale3d=0.01`：尺度 ≤ 0.01×scene_scale 走克隆，否则分裂；
  - `prune_scale3d=0.1`：尺度 > 0.1×scene_scale 直接裁剪（仅在 step > 3000 后启用）；
  - `revised_opacity=0.1`：分裂出的高斯不透明度调低（官方做法）。
- **验证**：尺度 max 从 25.99（发散中）被**精确**夹到 `0.2952 = 0.1 × scene_scale(2.9526)`；
  坐标范围 215 → 3.82（与 scene_scale 同量级）；30k 迭代耗时 90min → 34min。
- **教训**：对齐社区实现时要**逐条核对它做了哪些约束**。
  每条 prune / clamp / reset 都是防发散的，只对齐主流程等于没有对齐。
  这次属于"实现了官方的部分逻辑"，比完全没实现更难发现。

### G5.【已修复】PSNR 恒为 0（两个原因叠加，都不是渲染坏了）
- **现象**：训练日志 `评估 PSNR=0.00 dB`，但 loss 明明在下降。
- **原因一（调用层）**：调用 `evaluate(...)` 时少传参数导致整体错位
  （`opacities` 落到 `scales`、`background` 落到 `masks`），
  而各张量形状恰好兼容 → **不报错**，只是结果无意义。
- **原因二（评估集为空）**：`n_eval = ... if len(imgs) >= 10 else 0`，
  7 个视图时评估集为空 → `evaluate` 直接返回 `0.0`。
- **解法**：
  1. 改为**全部关键字传参**；`save_ply` 同样改为关键字传参（同类隐患）。
  2. 视图不足时**不留评估集**（留出 10% 会削弱小数据集训练），
     改为在训练视图上算 PSNR，并在日志与 metrics 里标注
     `psnr_on_train` / `psnr_views`，避免误读为泛化指标。
  3. 顺带新增诊断：训练结束时把 "渲染 | 真值 | 差异" 并排写到
     `04_train/diagnostics/render_vs_gt/`，用于肉眼确认位姿是否对齐。
- **验证**：PSNR 现在有真实数值（step 8000 达 **35.99 dB**），
  这同时**反证了相机位姿约定正确**（若轴翻转写错，PSNR 会在 8~10 dB 附近）。
- **教训**：多个同类型（都是 Tensor）的位置参数，顺序一错就是静默错误；
  对外函数调用尽量用关键字。

### F11.【误报自查】make_shortcuts 报告"已创建"但实际没有

- **现象**：脚本连续两次输出"已创建: C:\Users\admin\Desktop\gsflow Web GUI.lnk"，但文件不存在。
- **原因**：`WScript.Shell.Save()` 失败时 PowerShell 的**退出码仍是 0**，而脚本里的

- **教训**：凡是"调用外部程序做事"的步骤，都要在**自己的进程里复核产物**，不能信退出码。

## H. 算法与流程类

### D1. 黑背景 + 掩码：COLMAP 与 3DGS 的“掩码用法”不一样
- **问题**：黑背景图喂 COLMAP 效果最好（背景不产生特征），但训练时如果也让黑背景参与损失，
  模型会把背景学成一堆黑色高斯，前景质量被拖累。
- **解法**：
  - COLMAP：优先用 `--ImageReader.mask_path` 忽略背景；不支持时用纯黑图兜底（等价效果）。
  - 训练：掩码 PNG 同步到去畸变图同名下，**前 25% 迭代只在掩码内算 L1**，之后放开全图。
- **可调**：`train.mask_loss_until`（默认 0.25）。

### D2. `image_undistorter` 会把掩码一起做几何变换
- **问题**：直接把它指向 `02_masks` 会得到“变换后的掩码”，和去畸变图对不上；
  而且它的掩码语义是“0 表示忽略”。
- **解法**：喂给 undistorter 的一律是**全白掩码**（不忽略任何像素）；
  原掩码在准备阶段按 `name_map`（原名 → 去畸变名）映射，训练时按需缩放。
  见 `gsdata/colmap_io.py: prepare_undistorted()` 与 `stages/train.py: _sync_masks()`。

### D3. 密度控制的阈值必须按场景尺度归一化
- **问题**：官方 3DGS 用固定阈值（如 `> 0.01`）判断“高斯是否太小”，对大小不同的场景会失效。
- **解法**：`trainers/gsplat_trainer.py` 用相机中心平均距离估出 `scene_extent`，
  阈值取 `0.01 * scene_extent` / `0.5 * scene_extent`。

### D4. 密度控制改变张量形状后，优化器状态会失效
- **问题**：复制/裁剪高斯后，Adam 的动量缓存形状不匹配，轻则报错重则训练退化。
- **解法**：一旦高斯数量变化就**整体重建优化器与调度器**（`make_optimizers()`），
  与官方实现一致；不要试图 `clear()` 状态。

### D5. 不透明度没有任何上升压力 → 高斯“飘”在空中
- **解法**：每 3000 步把 logit 不透明度夹回 `0.1` 上限（官方做法），
  并在裁剪条件里加入“屏幕尺度 > 0.5*scene_extent”的超大高斯。

### D6. 导出 GLB：3DGS 的 PLY 不是带面网格
- **问题**：PLY 里只有高斯参数，没有三角形，常规 glTF 转换器会失败或产出垃圾。
- **解法**：我们的 `glb_points` 用 glTF `POINTS` 图元 + 顶点色（`KHR_materials_unlit`），
  任何 glTF 查看器都能打开；需要真网格（带三角面）时是另一条路线（SuGaR / 2DGS），
  已在架构里留作后续增强阶段。
- **SPZ**：更专业的压缩格式，但依赖第三方 `spz` 包；未安装时自动跳过并提示，不阻塞主流程。
