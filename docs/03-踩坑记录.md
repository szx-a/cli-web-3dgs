# 03 · 踩坑记录（实现全过程）

> 本文与记忆体 `cvcg` 同步。每条都写清：**现象 → 原因 → 解法 → 影响范围**。
> 目的：换台机器或换个人接手时，不用把这些坑再踩一遍。

---

## A. 环境与权限类

### A1. 工作区不可写，所有命令直接失败
- **现象**：`SetNamedSecurityInfoW failed (Win32 5): grantWrite(F:\3dgs-and-ai)` —— 连 `Get-Location` 都跑不了。
- **原因**：工作区目录缺少 `WRITE_OWNER` 权限，DSH 无法给它授予写权限；目录的权限项是继承自卷根的不完整集合。
- **解法**：用 DSH 自带的权限诊断脚本（`diagnose-windows-sandbox-acl`）为当前用户补一条完全控制项 + 重读校验。备份与回滚脚本落在 `F:\dsh-acl-recovery\`。
- **影响**：这是一切的前置；修好后 `pwsh` 才可用。

### A2. `D:\3dgs-workspace` 无法创建（沙箱只授权 F 盘）
- **现象**：`New-Item : 对路径"3dgs-workspace"的访问被拒绝`。
- **原因**：DSH 文件沙箱只允许写会话工作区 `F:\3dgs-and-ai`。
- **解法**：一次提权，在 D 盘建 `D:\3dgs-workspace`，并把 `env / workspace / tools / models / downloads`
  做成**目录链接（junction）**指向 F 盘真实目录。用户视角仍是 D 盘，写入实际落在沙箱授权区内。
  ```powershell
  New-Item -ItemType Junction -Path 'D:\3dgs-workspace\env' -Target 'F:\3dgs-and-ai\env'
  ```
- **影响**：之后所有安装/训练命令都不需要再提权。

### A3. `TEMP/TMP` 指向沙箱临时目录 → 到处 `WinError 5`
- **现象**：`ensurepip`、`get-pip.py`、`pip install -e .`、`pytest` 都报
  `PermissionError: [WinError 5] ... tmp6w3knrmn`（发生在 `shutil.rmtree` / `tempfile._resetperms` 里）。
- **原因**：沙箱临时目录 `C:\Users\admin\AppData\Local\Temp\dsh-XXXX` 里，Python 的临时目录清理会对文件做
  `chmod`（Python 3.13 在 Windows 上为删除只读文件而重置权限），这一步被沙箱拒绝。
- **解法**：把 `TEMP`/`TMP` 指到工作区内（`F:\3dgs-and-ai\env\tmp`）。
  代码层统一由 `paths.child_env()` 注入，脚本层在 `bootstrap.ps1` / `gsflow.cmd` 里设置。
- **注意**：`python -m venv` 仍然失败（venv 创建时会先 chmod 自己的临时目录），所以**建环境必须用 uv**。

### A4. `python -m venv` / `ensurepip` 不可用
- **现象**：`Error: Command '[...python.exe, -m, ensurepip...]' returned non-zero exit status 1`。
- **解法**：`uv venv <path> --python D:\python\python.exe`；pip 用 `uv pip install pip` 补进环境。
- **副作用**：uv 建的 venv 默认没有 pip，需要显式补一个（本项目已做）。

### A5. `pip install -e .`（PEP 517 构建）整条路走不通
- **现象**：`ERROR: Could not install packages due to an OSError: [Errno 13] Permission denied:
  'env\tmp\pip-build-tracker-xxx\...'`；改用 uv 也报同类错误（在 `uv-cache\builds-v0\.tmp...`）。
- **原因**：构建后端（setuptools/pep517）在临时目录里做 chmod/清理，与 A3 同源。
- **解法**：**放弃 editable install**，改为在 `site-packages` 放一个 `gsflow-dev.pth`，内容就是 `src` 路径。
  ```powershell
  Set-Content -Path 'env\venv\Lib\site-packages\gsflow-dev.pth' -Value 'F:\3dgs-and-ai\src' -Encoding ASCII
  ```
  控制台入口用 `scripts\gsflow.cmd` 代替 `gsflow.exe`。
- **影响**：`pip install -e .` 在本机永远不要用；装包一律 `uv pip install --python env\venv\Scripts\python.exe`。

### A6. `pytest` 的 `tmp_path` / `basetemp` 让整个 session 崩掉
- **现象**：测试能跑，但收尾时报 `PermissionError: os.scandir('...pytest-of-admin')`，
  接着 5 个用例全部 `ERROR`；更糟的是，清理中断会把测试临时目录的权限项**弄坏**，
  之后 `mkdir` 直接 `WinError 5`，需要提权 `icacls <dir> /reset /T` 才能恢复。
- **解法**：不用 pytest 的临时目录。`tests/test_smoke.py` 自定义 `workdir` fixture，
  目录放在 `env\pytest-tmp`；跑测试加 `-p no:cacheprovider`。
- **教训**：在这个环境下，任何“自动创建 + 自动删除临时目录”的库都要先验证。

### A7. `pwsh.exe` 不存在、脚本被执行策略拦住
- **现象**：`pwsh : 无法将"pwsh"项识别为 cmdlet`；`未对文件 bootstrap_m0.ps1 进行数字签名`。
- **原因**：本机只有 Windows PowerShell 5.1；`CurrentUser` 执行策略是 `RemoteSigned`。
- **解法**：`.cmd` 里调 `powershell.exe`；手动跑脚本加 `-ExecutionPolicy Bypass -File`。

### A8. PowerShell / curl 的 HTTPS 全部失败
- **现象**：`Invoke-WebRequest` 报 `基础连接已经关闭`；`curl.exe` 报
  `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`（错误码 000）。
- **原因**：沙箱里进程拿不到证书凭据（Schannel 凭据句柄失败）。
- **解法**：**所有下载改用 Python**（`urllib.request` 走 OpenSSL，正常）。
  已实现 `scripts/download_tools.py`（支持断点续传），需要新下载源时直接加进 `CATALOG`。

### A9. 控制台中文乱码
- **现象**：`gsflow doctor` 输出 `ϵͳ` 之类的乱码。
- **原因**：Windows PowerShell 5.1 控制台默认 GBK 代码页，Python 输出 UTF-8。
- **解法**：`.cmd` 里 `chcp 65001`；子进程环境加 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`。

## B. 硬件与 CUDA 类（本项目最关键的一条）

### B1. 文档里的 CUDA 11.8 在本机完全不可用
- **现象**：原工程文档写“CUDA Toolkit 11.8：与 3DGS 兼容性最佳”。
- **原因**：本机 GPU 是 **RTX 5060 Laptop（Blackwell，compute capability sm_120）**，
  驱动 573.22。CUDA 11.8（2022 年）不认识 sm_120，`nvcc -arch=sm_120` 直接失败；
  驱动也不接受 11.x 运行时。原版 `diff-gaussian-rasterization` 在 RTX 50 上编译失败是上游已知问题
  （[issue #1295](https://github.com/graphdeco-inria/gaussian-splatting/issues/1295)）。
- **解法**：
  - CUDA 用 **12.8.x**（与驱动 573.22 同代）或 12.9.x；
  - torch 必须 cu128+ 轮子（≥2.7 才含 sm_120 内核）；实测 `torch 2.11.0+cu128` 可用，
    `torch.cuda.get_device_capability()` 返回 `(12, 0)`，CUDA 张量运算正常；
  - 编译任何 CUDA 扩展前设 `TORCH_CUDA_ARCH_LIST=12.0`。
- **影响**：整个训练可行性；已把这条写进 `config`/文档/AGENTS。

### B2. gsplat “静默禁用”，报 `'NoneType' object has no attribute 'CameraModelType'`
- **现象**：`import gsplat` 成功，但一调用 `rasterization` 就:
  `AttributeError: 'NoneType' object has no attribute 'CameraModelType'`。
- **原因**：gsplat 的 `cuda/_backend.py` 在导入时判断 `cuda_toolkit_available()`；
  本机没有 nvcc → 它只打印一句黄字 `No CUDA toolkit found. gsplat will be disabled.`，
  然后 `_C = None`。真正的失败被这行日志掩盖了。
- **定位方法**：直接看 `gsplat/cuda/_backend.py` 的导入逻辑（不要只看报错栈）。
- **解法**：装 CUDA Toolkit（提供 nvcc）。安装脚本 `scripts/install_cuda.ps1` 已写成
  “只装 nvcc/头文件/库 + VS 集成，不动显卡驱动”，避免黑屏风险。
- **验证**：`python -c "from gsplat.cuda._backend import _C; print('ok')"`，
  第一次会现场编译内核（3~10 分钟）。

### B3. 显存只有 8GB（实际可用 ~6.5GB）
- **现象**：桌面应用（浏览器/微信/Steam）已占用 1.2~1.5GB。
- **解法（已内建）**：
  - `train.cap_max` 限制高斯数量（默认 150 万，可按场景下调）；
  - 渐进分辨率（前 15% 迭代半分辨率热身）；
  - 训练 OOM 时自动按 `1600→1400→1200→1000→800→600` 降档重试一次；
  - 训练前建议关掉浏览器等占显存程序。
- **经验值**：150~250 张图、长边 1400~1600、30k 迭代，8GB 可以跑完。

### B4. 内存只有 15.2GB（可用一度只剩 3.9GB）
- **注意**：COLMAP 全局匹配（exhaustive）在大数据集上吃内存，超过 ~500 张图建议用
  `sequential` 或 `vocab_tree`；同时避免和训练并发。

## C. 工具链类

### C1. COLMAP 官方 Windows 包给的是 `COLMAP.bat`，直接调用会失败
- **现象**：把 `COLMAP.bat` 当 exe 传给 `subprocess` 会报错或找不到 DLL。
- **原因**：bat 内部依赖同目录的 `bin\*.dll` 与插件，必须在自身目录下启动。
- **解法**：`tools/runner.py` 统一适配——`.bat/.cmd` 一律 `cmd.exe /c <bat> args`，并把 `cwd` 固定到脚本目录。
- **附带**：`COLMAP.bat` 不认 `-version`，版本探测要用 `colmap help`（已做 `VERSION_ARGS` 表）。

### C2. zip 解压后的目录层级不确定
- **现象**：FFmpeg 解压成 `tools/ffmpeg/bin/ffmpeg.exe`，COLMAP 解压成 `tools/colmap/bin/colmap.exe` + 顶层 bat。
- **解法**：`download_tools.py` 里 `flatten_single_dir()` 拍平多余层级；
  `locate.py` 的 `CANDIDATES` 同时列出 `bin/` 与顶层两种布局。

### C3. 网速极慢（实测 0.15~0.4 MB/s）
- **影响**：torch cu128 下载耗时 **47 分钟**；CUDA Toolkit 3.3GB 约需 3~5 小时。
- **解法**：
  - 所有大文件下载都实现**断点续传**（`download_resumable`，`.part` + `Range`，最多重试 200 次）；
  - `scripts/speedtest.py` 可测各源速度；
  - 若用户有更快通道（浏览器下载器/代理/离线包），把文件丢进 `downloads/` 同名即可被识别跳过。

### C4. `huggingface.co` 连通性不稳定
- **现象**：同一台机器上，socket+TLS 测试有时超时、有时成功；首次测试失败、稍后 `doctor` 显示可达。
- **解法**：配置里提供 `hf_endpoint`（推荐 `https://hf-mirror.com`）与 `http_proxy`/`https_proxy`；
  下载权重前先跑设置页的「测试 HuggingFace 连通性」。

### C5. COLMAP 3.12 开启 loop_detection 会直接崩溃（无 vocabulary tree）
- **现象**：`sequential_matcher` 在 `Generating image pairs with vocabulary tree...`
  处原生崩溃，退出码 `3221226505`（0xC0000409 STATUS_STACK_BUFFER_OVERRUN）。
- **定位过程**：先用 `--SiftMatching.use_gpu 0` 复现（排除显存/GPU），再单独加回
  `--SequentialMatching.loop_detection 1` → 必崩。即“开了闭环检测但没有 vocab tree 文件”。
- **解法**：**默认关闭闭环检测**；只有 `colmap.vocab_tree_path` 指向真实存在的
  vocab tree 文件时才启用（见 `stages/colmap.py`）。需要官方 vocab tree 时单独下载再填路径。
- **注意**：这个崩溃不带任何 Python 异常，`run_tool` 只能拿到退出码，因此错误信息里
  专门提示“看起来是原生崩溃”并列出三个高频原因。

### C6. COLMAP 选项名跨版本变化，写死参数会直接失败
- **现象**：`Failed to parse options - unrecognised option '--SequentialMatching.guided_matching'`。
- **原因**：COLMAP 3.12 把 guided matching 归到 `--SiftMatching.guided_matching`，
  早期版本则在 matcher 自己的命名空间下。
- **解法**：`tools/runner.py` 增加**选项能力探测**：抓 `colmap <subcommand> --help` 里的
  选项全集并缓存，执行前过滤掉当前版本不认识的“选项+取值”，同时在日志里 warn 出来。
  这样跨版本都能跑，而不是一升级就炸。

### C7. 阶段元数据文件被 COLMAP 当成图像
- **现象**：`E feature_extraction.cc:266] frames.json BITMAP_ERROR: Failed to read the image file format.`
- **原因**：COLMAP 会枚举 `--image_path` 下的所有文件，不做扩展名白名单。
- **解法**：元数据改用下划线前缀（`_frames.json`）并尽量少放；同时所有读目录的地方
  都按图像扩展名过滤（`IMAGE_EXT`）。

## C+. 训练数据准备类（在合成数据实测中发现）

### C8. `image_undistorter` 按“模型里的图像名”找文件，名字对不上就静默跳过
- **现象**：`02_images_clean` 有 36 张图，undistorter 日志只写
  `Undistorting image [1/5]`，输出目录只有 5 张，训练阶段随后报“找不到稀疏模型/图像”。
- **原因**：undistorter 遍历的是重建里的 `image.name`，到 `--image_path` 下按该名字找文件；
  我们早期把图像重命名成 `00000.jpg...` 再传进去，名字全对不上，于是只处理了恰好同名的那几张。
- **解法**：`prepare_undistorted()` 先 `read_model()` 取出**已注册图像名**，
  只复制这些文件、**保持原名**，并顺带报告“多少张找不到”（`missing`）。
  这条同时也解释了为什么训练必须有与 COLMAP 一致的原始图目录。

### C9. COLMAP 3.12 的去畸变输出布局变了：`sparse/` 而不是 `sparse/0/`
- **现象**：训练阶段报“找不到 COLMAP 稀疏模型：04_train\data\sparse\0”，
  但 `04_train\data\sparse\cameras.bin` 确实存在。
- **原因**：3.12 的 `image_undistorter` 把 `cameras.bin / images.bin / points3D.bin`
  直接写在 `sparse\` 下（还多了 rigs.bin / frames.bin）。
- **解法**：新增 `find_model_dir()`，依次尝试 `sparse/0`、`sparse`、`sparse/*` 三种布局；
  训练阶段的“数据是否就绪”判断也改用它。

### C10. `torch.from_numpy` 读到只读数组会告警（并可能引发未定义行为）
- **现象**：`UserWarning: The given NumPy array is not writable ...`。
- **解法**：`np.asarray(im, dtype=np.uint8).copy()` 后再转 tensor。

### C11. 分割失败时写 1x1 空掩码 → 下游拿到全黑图（静默废帧）
- **现象**：某张图没检出前景时，早期实现写了一个 `1x1` 的空掩码 PNG，
  清理图则是全黑；COLMAP 会把它当一张全黑照片吃进去（等价于丢帧但没有任何报错）。
- **解法**：新增 `mask.on_failure` 策略：
  - `keep`（默认）→ **原图直通**，清理图仍是原图，manifest 里单独记 `fallback_kept_original`；
  - `skip` → 明确丢弃该帧。
  并且全部失败时给出"已回退"的明确提示，而不是静默产出垃圾。

### C12. 模型权重没装时，无法验证 mask 阶段 → 增加零依赖兜底后端
- **背景**：FastSAM/rembg 需要下载权重，SAM2/SAM3 还需要 HF 授权；在下载受限的机器上
  mask 阶段完全无法验证。
- **解法**：实现 `classical` 后端（背景中位数估计 + RGB/色度距离 + Otsu 自动阈值 + 开运算），
  纯 numpy/PIL、无需任何权重。合成数据实测 **IoU 0.93~0.98**，足够用于静置物体与均匀背景。
- **附加收益**：`tests/test_mask_stage.py` 现在能在无 GPU、无权重、无网络的情况下
  回归整个 mask 阶段契约（掩码/黑背景/overlay/manifest/回退策略）。

### C13.【实测踩到】COLMAP 的掩码文件名规则是 `图片全名.png`，不是 `stem.png`
- **现象**：`E feature_extraction.cc:266] 00033.jpg MASK_ERROR: Failed to read the mask file.`
  —— 36 张图全部报错（后来只剩 2 张，见 C14）。
- **原因**：`--ImageReader.mask_path` 下，COLMAP 找的是 `<image_name>.png`，
  即 `00033.jpg` → **`00033.jpg.png`**；而我们内部习惯用 `00033.png`。
- **解法**：`imageops.mask_paths_for()/find_mask_path()` 统一两种约定；
  写入时**两种都产出**，读取时**两种都尝试**。并加了回归测试防止再退化。

### C14. 回退帧（未检出前景）漏写 COLMAP 命名掩码
- **现象**：修完 C13 后仍有 2 张报 MASK_ERROR，正好等于 manifest 里的
  `fallback_kept_original` 数量。
- **原因**：原图直通分支只写了 `{stem}.png`，漏了 `{image_name}.png`。
- **解法**：回退分支同样写两种命名。

### C15. 加了 mask 之后 `Check failed: max_num_matches > 0` 崩溃
- **现象**：`[sift.cc:89] Check failed: max_num_matches > 0 (0 vs. 0)`，退出码 0xC0000409。
- **原因**：COLMAP 的 `SiftMatching.max_num_matches` 在未显式指定、且部分选项组合
  （如 guided_matching 被版本过滤掉）下会取到 0，触发断言。
- **解法**：匹配命令显式传 `--SiftMatching.max_num_matches 32768`（可用
  `colmap.max_num_matches` 配置），不再依赖默认值。

## D. Windows 脚本与第三方库目录

### D1.【严重】`.ps1` 没有 BOM + 含中文 → PowerShell 5.1 解出满屏语法错误
- **现象**：跑 `install_cuda.ps1` 报
  `表达式或语句中包含意外的标记"寮€濮嬮潤榛樺畨瑁?.."`、`缺少右")"`、`赋值表达式无效`，
  但用 `read` 工具看文件内容完全正常。
- **原因**：Windows PowerShell 5.1 对**没有 BOM** 的 `.ps1` 按系统 ANSI（中文机器是 GBK）解码。
  我们写的是 UTF-8，中文字节被误解码后正好吞掉了字符串的结束引号，于是语法崩塌。
  （UTF-8 的无 BOM 依赖是 v7+ 的行为，5.1 不认。）
- **解法**：`.ps1` 一律写成 **纯 ASCII 内容 + UTF-8 BOM + CRLF**。
  校验两件事：
  ```powershell
  # 1) 前 3 字节应为 EF BB BF（UTF-8 BOM）
  [System.IO.File]::ReadAllBytes($f)[0..2] | ForEach-Object { $_.ToString('X2') }
  # 2) 语法检查（$errors 为空即通过）
  [System.Management.Automation.Language.Parser]::ParseFile($f, [ref]$null, [ref]$errors)
  ```
  已修：`scripts\bootstrap.ps1`、`scripts\install_cuda.ps1`（均 BOM + 语法 OK）。
- **同类教训**：任何“被外部程序按 ANSI 解码”的文本都要小心——包括用 PowerShell 的
  `Get-Content/Set-Content` 去改含中文的 UTF-8 源码（见 B 组第 8 条，把 `frames.py` 写坏过）。

### D2. ultralytics 想写 `AppData\Roaming` → `WinError 5`
- **现象**：`import ultralytics` 报 `PermissionError: [WinError 5] 拒绝访问。: 'C:\Users\admin\AppData\Roaming\Ultralytics'`。
- **原因**：ultralytics 首次导入会在用户 Roaming 目录建配置。沙箱只授权工作区。
- **解法**：**导入之前**设置 `YOLO_CONFIG_DIR` 到工作区（`paths.runtime_env()` 统一注入，
  `scripts\gsflow.cmd` 也设了）。同理 matplotlib 需要 `MPLCONFIGDIR`。

- **现象**：管理员运行 `install_cuda.ps1` 后，安装器返回 `-522190823`（= `0xE0E00019`），
  D 盘没有生成 CUDA 目录，脚本预期的 `logs\cuda_install.log` 也没生成。
- **已验证的部分**（排除掉的可能性）：
  - 安装包完好：3213.2 MB，`ProductName = NVIDIA Package Launcher`，**数字签名 Valid（NVIDIA Corporation）**；
  - 组件名合法：NVIDIA 自己的 setup 日志里有
    `Found 66 sub-package config files - 0 excluded - 66 selected unique`，
    并且逐个加载了 `nvcc_12.8` / `cudart_12.8` / `CUDADevelopment_12.8` 等包；
  - 安装器确实启动过：`%LOCALAPPDATA%\Temp\NvidiaLogging\Log.4828setup.exe.log`（177 KB）。
- **关键观察**：那份 NVI2 日志只覆盖“加载清单 → 缓存安装包 → 卸载扩展 DLL”这一段（约 2.3 秒），

  并给出三条降级路径（显式组件名 / 交互式只勾 Development / 干脆不装）。
- **重要结论**：**除训练阶段外，其余阶段都不需要 CUDA**。
  测过：frames / mask / colmap / export / metrics 全部可在无 nvcc 环境下工作。

### F4.【关键突破】不需要管理员权限的"便携 CUDA"
- **思路**：官方 CUDA 安装包（`cuda_12.8.1_572.61_windows.exe`）本质是 **7z 自解压包**，
  而 Windows 10+ 自带 `bsdtar`（`tar.exe`）**能读 7z**。于是：
  ```bat
  tar -xf downloads\cuda_12.8.1_572.61_windows.exe -C env\cuda_pkg cuda_nvcc cuda_cudart cuda_cccl
  ```
  只取三个子包，拼成 `tools\cuda`：**358 MB，含 nvcc 12.8.93，全程零管理员权限**。
  - `cuda_nvcc/nvcc/` → `tools\cuda\`（bin / nvvm / include）
  - `cuda_cudart/cudart/include` + `lib\x64` + `bin` → 对应标准位置
  - `cuda_cccl/thrust/include` → `tools\cuda\include`
  - 另把 `tools\cuda\bin\crt\*` 复制到 `include\crt\`
  已封装为 `scripts\build_portable_cuda.cmd`，并加了 `paths.find_portable_cuda()` 自动识别。
- **意义**：`0xE0E00019` 那类安装器问题可以完全绕开；把 3.2GB 安装包变成 358MB 可移植工具链。

### F5. nvcc 还需要 `cl.exe`（vcvars 环境）
- **现象**：便携 CUDA 就绪后 `nvcc` 报 `nvcc fatal : Cannot find compiler 'cl.exe' in PATH`。
- **原因**：nvcc 不是独立编译器，主机端要调用 MSVC 的 cl.exe。
- **解法**：`scripts\gsflow_gpu.cmd` 先 `call vcvars64.bat`（自动在 VS2022 BuildTools /
  VS2022 / VS2026 之间找），再设置 `CUDA_HOME` / `TORCH_CUDA_ARCH_LIST=12.0` 并执行 gsflow。
- **踩坑**：`.cmd` 里**不能用带括号的 if 块**——`C:\Program Files (x86)\...` 里的 `(x86)`
  会让 cmd.exe 把它当成代码块结束符，报
  `\Microsoft was unexpected at this time.`。必须改成 `if ... goto label` 的写法。
- **另一个坑**：`.cmd` 文件**不能带 UTF-8 BOM**，cmd.exe 会把 BOM 当命令的一部分。

### F6. 【关键】中文 Windows 下 torch 解码编译器的输出会崩
- **现象**：gsplat 编译内核时报
  ```
  File "torch/utils/cpp_extension.py", line 502, in get_compiler_abi_compatibility_and_version
    match = re.search(r'(\d+)\.(\d+)\.(\d+)', compiler_info.decode(*SUBPROCESS_DECODE_ARGS).strip())
  UnicodeDecodeError: 'cp1' codec can't decode bytes in position 0--1: No mapping for the Unicode character exists
  ```
  最终表现为 `_C = None` + `'NoneType' object has no attribute 'CameraModelType'`。
- **原因**：`torch.utils.cpp_extension.SUBPROCESS_DECODE_ARGS` 默认是 `('oem',)`；
  中文 Windows 下 cl.exe 输出 UTF-8（控制台代码页 65001），用 OEM 码页解码必然失败。
  这个解码错误发生在 torch 内部，只在 gsplat 的 VERBOSE 输出里才看得到，非常隐蔽。
- **解法**：在 `paths.apply_runtime_env()` 里把
  `torch.utils.cpp_extension.SUBPROCESS_DECODE_ARGS` 改成 `('utf-8',)`
  （CLI 与 GUI 入口都会自动应用）。可用
  `env\venv\Scripts\python.exe -c "import torch.utils.cpp_extension as ce; print(ce.SUBPROCESS_DECODE_ARGS)"`
  验证。
- **附带**：`.cmd` 里同时设 `VSLANG=1033` 让 MSVC 输出英文，减少中文字节带来的概率性失败。

### F8.【关键】ninja 在本环境"干完活但不退出" → torch 永久卡死
- **现象**：gsplat 编译内核时 `ninja` 进程 CPU=0、构建目录只有 build.ninja、日志为空、永不结束。
- **定位**：用最小 build.ninja 测试——**任务确实完成了**（`out.txt` 已生成），
  但 ninja 进程不退出；官方版与 MinGW 版两个 ninja 都一样。
  而 `torch.utils.cpp_extension._run_ninja_build` 是**同步等待 ninja 退出**的，于是永远卡住。
  （另有一个次要原因：上一次失败留下的 `lock` / `.ninja_lock` 会让 ninja 直接挂起。）
- **解法**：**绕过 ninja**——`src/gsflow/build.py` 直接解析 torch 生成的 `build.ninja`，
  自己调用 cl.exe / nvcc.exe / link.exe；`paths.apply_runtime_env()` 检测到 ninja
  不可用（20 秒探针）时把 `_run_ninja_build` 换成它。可用 `GSFLOW_FORCE_NINJA=1` 强制回退。
- **附带修掉的 4 个坑**（都在 build.py 里）：
  1. cl.exe 命令里带着 GCC 风格参数（`-O3 -Wno-attributes`）→ `D8021 无效的数值参数`，
     整批 .cpp 编译失败 → 做参数归一化（`-O3`→`/O2`，`-W*` 剔除）。
  2. 链接命令里 `C$:\Program Files\...` —— ninja 的 `$:` 转义没解开 → 链接器报
     "filename, directory name, or volume label syntax is incorrect" → 展开后再解一次转义。
  3. `cub/cub.cuh` 间接引入 Windows `rpcndr.h` 的 `#define small char`，
     把 torch 头里 `StreamSegmentSize(..., bool small, ...)` 的参数名替换成 `char`
     → `invalid combination of type specifiers`。`-Xcompiler /Usmall` 与 `-Dsmall=` 都太晚/无效，
     最终用**头文件遮蔽**：在 include 路径最前面放一个同路径头，先 undef 再 include 真正的头。
  4. `/showIncludes` 产生的上万行 "注意: 包含文件" 灌爆日志 → 编译时剔除该参数。

### F9.【关键】相机位姿翻转写错 → alpha 恒为 0、密度控制完全不触发
- **现象**：训练能跑完，但 `alpha 和 = 0`、`means.grad.abs().sum() = 0`，
  高斯数量从 427 到结束都不变，PSNR 为 0（只有不透明度/颜色被优化，loss 会缓慢下降，很具迷惑性）。
- **原因**：`load_colmap_data` 里照抄 gsplat 示例写了 `c2w[0:3, 1:3] *= -1`（y、z 都翻），
  这在本流程的数据上把**所有点放到了相机背后**（相机空间 z 全为负）。
- **定位方法**：`scripts/probe_pose_convention.py` 扫 4 种翻转组合，统计"相机前方点数 / alpha 和 / 位置梯度"：
  ```
  y*+1 z*+1   alpha 和=7249.5   前方点 427/427   梯度 7.9e-02   ← 正确
  y*+1 z*-1   alpha 和=0.0      前方点 0/427     梯度 0.0
  ```
- **解法**：只翻 y（`c2w[0:3, 1] *= -1`）。
- **教训**：训练"能跑完"不等于"在工作"。必须断言 alpha 非零与梯度非零，
  所以在 `train()` 里保留了 step 1 的探针（alpha 和 / 可见像素 / 梯度）。

### F10. 密度控制的三处逻辑错误（修完才开始真正加密）
1. **阈值量纲**：官方 0.0002 是对位置梯度**取平均**的量纲；我们用的是每个高斯的梯度范数
   （实测均值 ~2e-4、最大 ~1.2e-2），直接用会让加密几乎不发生 → 校准为 `1.5e-4` 并可配置。
2. **条件互斥**：早期把"梯度过阈"和"尺度过小"做**与**，实测两组点交集为 0
   （梯度过阈组尺度均值 0.45，尺度过小组梯度不够）→ 改为**只按梯度选候选**，
   在加密时对**小尺度克隆、大尺度分裂**（官方策略）。
3. **顺序 + 裁剪规则**：早期"先裁剪后复制"，而两个掩码都按裁剪前的张量算，索引立刻失效；
   而且把"尺度过大"也当裁剪条件，会立刻删掉刚加密出来的点
   （实测 427 → 加密 46 → 又被裁 78 → 只剩 395，做了负功）。
   现在：**先加密（掩码最先用）→ 再按不透明度裁剪**。

### G6.【已修复·决定训练成败】相机位姿**不需要任何轴翻转** + 初始尺度必须用最近邻
这两个问题合起来让 PSNR 长期卡在 13~14 dB（现在的水平是 34.79 dB，**留出视图**）。

**(1) 相机位姿不翻转**
- 我先后用过 `c2w[0:3, 1:3] *= -1`（照抄 gsplat 示例）和后来"修"成的
  `c2w[0:3, 1] *= -1`，**两者都是多余的**。
- 官方 `examples/datasets/colmap.py` 的做法：
  ```python
  w2c = [[R|t],[0|1]]          # COLMAP: world -> camera
  camtoworlds = np.linalg.inv(w2c)   # 直接求逆，不翻任何轴
  ```
  而本项目 `colmap_io.Image.cam_to_world()` 返回 `(R.T, -R.T @ t)`，
  正是 `inv([[R|t],[0|1]])` 的解析解 —— **完全等价**，所以额外翻转都是错的。

**(2) 初始尺度必须用最近邻距离，不能用"到质心距离"**
- 官方 `create_from_pcd`：`dist2 = distCUDA2(points)`（到最近邻的平方距离均值），
  `scales = log(sqrt(dist2))`。
- 我原来用"到点云质心的距离 × 0.5"。对一块平面，质心到各点距离≈平面半径（本例 ~1.0），
  于是初始高斯有半个场景那么大 → 整幅图被少数巨大高斯糊住 → 渲染是一片带颜色的雾。
- 改成最近邻后初始尺度 1.0 → **0.031**（≈ 官方 `scene_scale*0.01` 量级），
  PSNR 立刻从 18.9 跳到 **33.75 dB**。
- 实现见 `_init_scales_nn()`（分块 cdist，避免大场景构造 N×N 矩阵）。

**(3) 怎么定位的（方法论，值得记住）**
- **无效判据**："把稀疏点当小高斯渲染再算 PSNR"。
  1846 个点渲染成小圆点覆盖不到整张图，两种位姿约定都只有 ~10 dB，没有判别力。
- **有效判据**：投影 + 纹理一致性（新增 `scripts/verify_pose_projection.py`）。
  把 COLMAP 稀疏点投影成像素，再看该处图像梯度：
  ```
  不翻转   点处梯度 21.17 / 全图 2.62 = 8.07x   ← 正确（与官方一致）
  翻 y     点处梯度 12.40 / 全图 2.62 = 4.73x
  ```
- **教训**：判断几何问题要找**能在几何上直接证伪**的判据（投影是否落在特征上），
  而不是拿间接指标（PSNR）硬试。

### G7.【已修复】不透明度重置必须配套"重置后重新致密化"
- 官方每 3000 步把不透明度压回 0.01，**紧接着会对所有高斯做一次 densify** 补回容量。
- 我只实现了"压回 0.1"、漏了配套的补回步骤，等于每次重置都把模型打掉一大半。
- 实测（同一份数据，只改这一个开关）：
  | 配置 | step 6000 PSNR | 最终 |
  |---|---|---|
  | 重置开 + 密度控制开 | 21.47 | 21.47 |
  | 重置开 + 密度控制关 | 19.02 | 19.02 |
  | **重置关** + 密度控制关 | **36.28** | **36.44**（稳定上升） |
- 因此本项目默认 `opacity_reset_interval = 0`（关闭）。
  **若要开启，必须先实现"重置后致密化"**，否则不要打开。

### G8.【已修复】加密阈值不要做"分位数自适应"
- 官方用的是**固定绝对阈值**（`grow_grad2d = 0.0002`，作用在按视图累积的 2D 屏幕梯度上）。
- 我一度改成"取梯度范数的 (1-q) 分位作阈值"，结果梯度一衰减阈值就跟着降 →
  **无限膨胀**（6000 步涨到 6 万高斯，PSNR 从 33.75 掉到 21.47）。
- 关键认识：**梯度随优化自然衰减，本身就是"该停止加密"的信号**，
  不需要（也不应该）人为跟随。现已改回固定阈值（`densify_grad_threshold = 2e-4`），
  `densify_quantile` 默认 0（仅保留作实验开关）。

### G9.【已修复】PLY 的表示约定：scale 是 log 值、opacity 是 logit
- 官方 inria PLY 约定：`scale_* = log(真实尺度)`、`opacity = logit(概率)`。
- 我的 `save_ply` 收到的是已 `exp` 的真实尺度和已 `sigmoid` 的概率，却原样写入，
  于是导出阶段 `_read_ply` 又 exp 一次 → 尺度放大 **200 倍**（0.005 → 1.005），
  渲染成一片糊住画面的灰雾。
- **注意影响面**：训练内的诊断渲染直接用内存参数、不经过 PLY 往返，
  所以 PSNR 34.79 dB 那个结果**是可信的**；受影响的只有导出产物
  （GLB / 预览图 / 查看器）。
- 已修：写盘时 `log(clamp(scales))` 与 `logit(clamp(opacities))`，
  与官方 PLY 对齐，SuperSplat / three.js 也能正确读。

### G10. 预览图要用真实渲染，不要用散点图
- 原来 `_render_previews` 用 matplotlib `ax.scatter` 画高斯**中心点**，
  得到的是一团点云 —— **一个 PSNR 35dB 的好模型和一堆乱点长得一样**，
  完全无法反映重建质量（我因此误判了好几轮）。
- 现改为 gsplat 无头真实渲染：相机优先取**训练时的真实位姿**
  （自己估的环绕相机很容易取景失当，实测渲成一片纯背景色），
  有真值图时把"渲染 | 真值"并排拼一张，可直接对照。
- gsplat/CUDA 不可用时自动退回散点图，保证导出阶段仍可独立运行。

### G11.【已修复】COLMAP 度量读错了列
- `images.txt` 每行是 `IMAGE_ID QW QX QY QZ TX TY TZ CAMERA_ID NAME`，
  第 8 个字段（索引 7）是 **TY（相机平移分量）**，不是重投影误差！
  早期代码读的正是 `parts[7]` → "平均重投影误差"实际是相机 TY 的均值
  （实测 99.987px，看着像标定崩了，其实重建误差只有 0.8px），
  还会误触发 "> 2.0px 标定可能不稳定" 的告警。
- 真正的逐点重投影误差在 `points3D.txt` **第 8 列**（`POINT3D_ID X Y Z R G B ERROR TRACK[]`）。
- 同时修注册率统计：原来 `len(parts) >= 10` 会把每张图的 POINTS2D 行也算上
  （16 张报成 32 张），改为只统计位姿行（第 10 列是图片文件名）。
- 修复后：注册 36/36、平均重投影误差 **1.08px**，与 COLMAP 自报的
  "Number of images: 36" 一致。

### G12.【已修复】合成基准数据本身是坏的
- 平面角点是 `(±hs, ±hs, 0)`（位于 z=0、法线朝 +z），而相机轨迹是
  `(r·cosθ, 小高度, r·sinθ)` —— θ=0 时相机在 `(r, 0.15, 0)`，
  视线几乎与平面**平行**，平面被侧视成一条线；相机高度只有 0.15（仰角 2.4°），
  基线也几乎退化。渲染出来是一张几乎全黑的图。
  后果：SIFT 无特征，36 张只注册 14 张，重建无从谈起。
- **还有第二个坑**：`render_view` 用单应 + `PIL.Image.transform`。
  单应矩阵本身算对了（`H @ src` 精确等于目标图像坐标），
  但 PIL 的 fillcolor/逆映射/越界约定把整块四边形填成黑色，**且不报任何错**。
- 修法：相机改为**绕平面法线（+z）环绕**并向 +z 侧抬高，始终正对平面；
  渲染改成**逐像素光线投射**（对每个像素发射线求与平面交点再采样纹理），
  从第一性原理出发、完全可控，不依赖图像库的隐式约定。
- 效果：注册率 14/36 → **36/36**，图像成为铺满纹理的平面。

> 这一批（G6~G12）的共同教训：**"配置/约定类"的错误几乎都是静默的**。
> 它们不报错、不崩溃，只是让结果变差，而且很容易被误判成"算法不行"。
> 对付它们的办法是**找一个能在几何上直接证伪的判据**，
> 以及**对齐官方实现并逐条核对它做了哪些约束**。

### G13. 分割后端的选择会直接决定 COLMAP 注册率（实测对比）
同一份合成数据、同一套参数，**只换 `mask.backend`**：

| 后端 | 前景占比 | COLMAP 注册率 | 稀疏点 | mask 耗时 | 最终 PSNR |
|---|---|---|---|---|---|
| fastsam（默认） | 22.8% | **16/36** | 1850 | 12.5 s | 21.13 dB |
| **classical** | 14.5% | **36/36** | 3146 | 4.3 s | **33.34 dB** |

- **原因**：合成场景的"主体"是一块**铺满纹理的平面**。fastsam 按语义/物体边界切分，
  在这类非自然场景上会把一部分纹理判成背景切掉（前景占比偏高到 22.8%），
  COLMAP 的可用特征随之减少，注册率直接腰斩。
  而 classical 是 Otsu/背景模型分割，对"平面 vs 深灰背景"这种高对比场景非常准。
- **但不能因此把 classical 设为默认**：真实照片里有杂物、阴影、渐变背景，
  靠颜色阈值会失效，而 fastsam 的语义分割更稳。所以：
  - 默认仍是 `fastsam`（面向真实使用场景）；
  - **背景干净**（纯色墙、桌面、影棚）时改用 `--set mask.backend=classical`，
    会明显更快更准。
- **教训**：**分割质量不是"好看不好看"，而是会直接改变下游 SfM 的成败。**
  换后端时要盯的指标是**注册率**，不是掩码图看起来是否干净。
  本项目在 `colmap` 阶段已经会对注册率低于阈值发出告警，这就是它的用处。

### G14.【选型】点云 → 网格：SuGaR 在本机不可行，改走 TSDF 融合
用户反馈"点云 GLB 没有实感"，希望拿到能进 Blender / 引擎的三角网格。调研三条路线：

| 路线 | 结论 | 依据 |
|---|---|---|
| **SuGaR** | ❌ **本机不可行** | 官方 Windows 移植版要求 `pytorch==2.0.1 + pytorch-cuda=11.8 + pytorch3d==0.7.4`。本机是 RTX 5060 / **Blackwell sm_120** / CUDA 12.8：torch 2.0.1 不含 sm_120 内核、pytorch3d 无对应 wheel，其自带 viewer 还明确写着不支持 Windows。走通等于把图形栈降级到 2023 年并与驱动冲突 |
| **2DGS / 2D-surfel-gaussian** | ⚠️ 后续可选 | gsplat **自带 2DGS 光栅化**（本机已编译 `RasterizeToPixels2DGS*`），但 2DGS 是另一套训练方式（surfel + 法线一致性 + 深度畸变正则），且网格提取仍需自己实现 |
| **TSDF 融合** | ✅ 本次采用 | 用已训练的 3DGS 渲深度+RGB → open3d 融合。不改训练栈、无版本冲突、8GB 显存可跑 |

社区参考实现：[19reborn/neural-texture-splatting/extract_mesh_tsdf.py](https://github.com/19reborn/neural-texture-splatting/blob/main/extract_mesh_tsdf.py)
用的是**张量版** `o3d.t.geometry.VoxelBlockGrid` + `compute_unique_block_coordinates`。

**实测**（真实素材 real-tuned 模型，60 视角 @512px）：167,731 三角形 → 保留最大连通块后
**160,068 面 / 87,598 顶点**，`is_edge_manifold()=True`（边流形，水密性良好），导出耗时约 85 秒。

### G15. TSDF 网格导出的 5 个坑（每个都让人卡很久）
1. **`ScalableTSDFVolume` 会固定分配 512³**：`extract_triangle_mesh()` 内部申请
   `(512,512,512,3) float32` = **1.50 GiB**，本机 15.2GB 内存下直接 `MemoryError`，
   而且**不受 `voxel_length` 影响**、无法调低。
   解法：换张量版 `VoxelBlockGrid`（稀疏块存储，内存随"表面附近的块数"增长）。
2. **`UniformTSDFVolume` 的 `origin` 要 numpy 向量**：open3d 里**没有 `Point3D` 这个类型**
   （我照着旧文档写 `o3d.geometry.Point3D(...)`，报 `AttributeError`）。
3. **gsplat 的 `colors` 带 batch 维**：形状是 `(C, H, W, ch)`。
   写 `colors[0][..., :3]` 会去切**空间维**，得到 `(H, W, H, 3)`，
   后续在 integrator 里报 `array is 2-dimensional, but 3 were indexed`。
   正确写法：先 `img = colors[0]`（得到 `(H,W,4)`）再切通道。
   > 这个坑靠"打印形状"才定位到 —— 猜了三轮都不对。
4. **`alpha` 是 `(H,W,1)`、`depth` 是 `(H,W)`**：直接 `alpha > t` 会**广播成 `(H,W,H)`**，
   `valid` 的形状变成三维、掩码语义完全错乱。必须先 reshape 掉尾部 1。
5. **`compute_unique_block_coordinates` / `integrate` 要 `o3d.t.geometry.Image`**，
   不是裸 `o3d.core.Tensor`（传 Tensor 报 `TypeError: incompatible function arguments`）。

**方法论**：这一处我明显陷入了"改一行、跑一次、看一个错"的循环。
转折点是**去读社区实现**（那份 `extract_mesh_tsdf.py` 一次就把正确的 API 组合、
通道处理、无效深度置 0 的做法全给了）。**先找成熟实现，再动手** 又一次被验证。

### G16.【已实现】网格导出补上**泊松重建**路线 + 网格质量的可量化验证
> 用户提醒"你不考虑泊松吗" —— 确实该考虑。这条比 TSDF 更贴合"点云没有实感"的诉求。

**为什么泊松更合适**：它输出**天然闭合（水密）**的表面，正是"实体感"的来源；
而 TSDF 依赖多视角深度一致性，对视角缺口 / 薄壳开口很敏感
（实测碗类物体只出一层内壁、边缘破碎）。

**社区标准流程**（已落地 `poisson_mesh()`）：
1. 统计离群点剔除
2. 法线 —— **优先取高斯旋转的局部 +z 轴**（3DGS 训练时会把高斯压扁对齐表面，
   朝向里就含表面信息），拿不到再退回 `estimate_normals`
   + `orient_normals_consistent_tangent_plane`。
   **法线朝向决定泊松成败**：乱了就出翻边/破洞。
3. `create_from_point_cloud_poisson(depth=9)`
4. **按密度分位数裁掉低密度区** —— 泊松会在无数据处"鼓包"，这步不能省
5. 裁到主体包围盒 / 只留最大连通块

导出阶段现在两条路线可选：`--set export.mesh_method=poisson|tsdf`（默认 poisson）。
实测泊松输出 **387,728 三角形 / 19.4 万顶点**（TSDF 是 15 万面）。

**新增量化验证**：`scripts/verify_mesh_quality.py`
本机 open3d 的 Filament **离屏渲染在无窗口环境返回全黑图**（怎么调相机/加灯都没用），
所以"看图"这条路走不通。改用**轮廓 IoU**：A=高斯渲染的 alpha 轮廓，
B=网格光栅化轮廓，IoU 衡量几何贴合度；同时把 A/B/差异拼图存盘以便肉眼定位。

**诊断结论（重要，避免继续在错误方向调参）**：
泊松网格的轮廓 IoU 只有 **0.267**。轮廓对比图显示：
- 高斯模型轮廓是**一大团**，网格只有**碗内壁**，网格完全被模型包住；
- 该模型掩码是正常应用的（122/122，前景 29.1%），但训练时
  `mask_loss_until=0.25` —— **掩码内损失只在前 25% 迭代生效**，
  之后背景无人约束，浮点数在背景里长起来把轮廓撑大。

⇒ **网格质量的天花板由"模型本身"决定，不在提取算法。**
下一步该做的是让训练全程约束在掩码内 / 改进浮点抑制，
而不是继续调 TSDF 的体素或泊松的 depth。

### G17.【已修复·网格质量最大的一项】泊松的密度裁剪默认值把质量砍半

### G18.【已实现·决定性改进】网格提取必须走"深度反投影"，不能直接拿高斯中心喂泊松
> 用户给出了社区标准流程（深度反投影 → 预处理 → 泊松 → 后处理），这条纠正了我一个根本性错误。

**错误做法**：直接把 3DGS 的高斯中心当点云喂给泊松。
问题在于高斯中心是**一团一团分布在"表面附近的三维体"**，不是薄壳 ⇒
泊松在无点区域鼓包、在点密集处过拟合。
实测症状：网格轮廓只有模型轮廓的 **0.20**（网格只有物体的 1/5 大）、轮廓 IoU 0.238。

**正确流水线**（已实现，`export.mesh_method=poisson` 默认）：

| 步骤 | 实现 | 作用 |
|---|---|---|
| ① 渲深度 | `render_depths()`（RGB+ED）+ 不透明度/深度一致性过滤 | 拿到可信表面像素 |
| ② **反投影** | `backproject_depth_to_points()`（新增） | 得到**紧贴表面**的稠密点云，法线天然朝外 |
| ③ 下采样 | `voxel_downsample()`（新增，纯 numpy） | 均匀化密度，防泊松过拟合 |
| ④ 泊松 | `poisson_mesh()` + 一致定向 | 隐式函数拟合 |
| ⑤ 平滑 | `smooth_mesh()` Taubin（新增） | 去阶梯噪点，且不像拉普拉斯那样收缩体积 |
| ⑥ 简化 | `simplify_mesh()` QEM（新增） | 400 万面 → 40 万面 |

**实测（122 视图真实素材，75 视角 @640px）**：
反投影 2,579,017 点 → 下采样 2,311,406 点 → 泊松 3,960,389 面 → 平滑 → QEM 385,151 面。

**与旧路线的客观对比**（同一验证脚本）：

| 指标 | 旧（高斯中心） | 新（深度反投影） |
|---|---|---|
| 网格轮廓/模型轮廓 | 0.20（网格只有物体 1/5 大）| **1.44**（尺寸正确）|
| 轮廓 IoU | 0.238 | **0.650** |
| 深度相对误差中位数 | 1.77% | 2.53% |

旧路线深度误差反而略小 —— 因为它只覆盖最确定的很小一块区域，
**但根本不成形**，没有实用价值。这也说明**单一指标不能作为唯一判据**。

### G19. 网格 GLB 导出 + `validate_glb` 按图元模式分别校验
用户明确要求"加模型的 glb 格式导出"。新增 `_write_mesh_glb()`：
glTF 2.0 二进制、**TRIANGLES 图元 + 顶点色**，可直接拖进
Blender / Unity / three.js / Windows 自带「3D 查看器」。

三个必须注意的点：
1. **索引用 uint32** —— 顶点可能上百万，uint16（65535）会溢出。
2. **y/z 取反** —— glTF 是 Y 轴向上，COLMAP 是 Y 向下，不翻会让模型倒立。
3. **统一三角形绕序为逆时针** —— 否则法线朝内，查看器里看起来是黑的。

同时把 `validate_glb()` 从"只认 POINTS"扩展成按模式分别校验：
- POINTS：POSITION 与 COLOR_0 顶点数一致
- TRIANGLES：必须有 indices、索引数是 3 的倍数、索引 componentType 合法、
  **索引上界不越界**（越界会让查看器黑屏或崩溃，而且不会报错）
  实测两个 GLB 均通过：`model_mesh.glb`（mode=4，385,151 面）、`model.glb`（mode=0）。

### G21.【已实现】纹理烘焙 —— 顶点色 → 贴图，最后一步"实感"

### G22.【已修复·严重】GLB 的位置数据被写了两遍

```python
...

```
于是 blob 变成 `pos + pos + color + idx`，**索引整体后移**，

### G26.【已修复】gsplat 每次 import 都重编内核（80~140 秒 → 0.2 秒）
环境修好后，预览渲染真的去**现场 JIT 编译** gsplat 内核，测试里单个用例 5 秒变 86 秒。
顺藤摸下去发现更根本的问题：

* `gsplat/cuda/_backend.py` 的 `load_extension()` **总是**调用 `_jit_compile()`，
  它指望 ninja 做增量构建；
* 但本环境 **ninja 不退出**，我们换成了自己的构建器（`build.py`）；
* ⇒ 每次 import 都走一遍"重新链接"，实测 80~140 秒。

**正解**：在 gsplat 之前把已编译的 `.pyd` 加载好并注册进 `sys.modules`，
让 `_backend.py` 的 `from gsplat import csrc as _C` **命中缓存**，
`except ImportError` 的 JIT 分支根本不会执行。

这里**连续踩了四个坑**（顺序错了就前功尽弃）：

| # | 坑 | 症状 |
|---|---|---|
| 1 | 模块名必须是 `gsplat_cuda` | `dynamic module does not define module export function (PyInit_xxx)` |
| 2 | 必须在 `import torch` **之后**加载 | `DLL load failed ... 找不到指定的模块` |
| 3 | **必须同时注册 `gsplat.csrc`** | import gsplat 很快，但**第一次 rasterization 才开始重编** |
| 4 | 必须在 `_patch_torch_ninja_bypass()` **之前** | `LINK : fatal error LNK1104: 无法打开文件"gsplat_cuda.pyd"` |

第 4 条我绕了好几轮：先加载了 `.pyd`，torch 又决定重编，链接器无法覆盖
**已加载进内存**的 DLL。最后靠"**打印每一步耗时**"才看清是顺序问题，
而不是机制不对。

**结果**：`apply_runtime_env` 0.09s + `import gsplat` 0.02s + 首次光栅化 0.30s。
测试套件 **86 秒 → 4 秒**；网格预览从"放弃"变成真的出图。

> 顺带修正 `_splat_kernel_ready()` 的判据：早期写成"看扩展目录里有没有 `.pyd`"，
> 结果在**没预加载**的进程里误判为就绪、照样触发 86 秒编译。
> 现在判据是 `sys.modules["gsplat.csrc"] 存在且 _C 不为 None`。

### G30. 网格密度裁剪：要用**很小的**阈值，且不能用"看起来合理"的分位数
`poisson_mesh(density_quantile=)` 的本意是"用密度图把低密度区域的包络面删掉"，
但我一度用 `0.03`，实测把轮廓 IoU 从 0.68 砸到 0.32。

扫描（同一模型，5 视角 @224px）：

```
  crop_q  dens_q  depth   triangles     IOU
    0.90   0.000      9      443522   0.692
    0.90   0.001      9      443153   0.696
    0.90   0.005      9      441039   0.466   ← 0.005 就崩
    0.95   0.000      9      481423   0.725
    0.95   0.001      9      481023   0.750   ← 最佳
    0.95   0.005      9      478692   0.614
```

**根因**：用的是**全局分位数**。模型正对相机的区域观测多、密度高，
侧面观测少、密度低 —— 一个全局阈值必然误伤侧面。
泊松在"完全无观测"处的密度接近 0，所以阈值必须取**很小**的值。
⇒ 默认改为 `density_quantile=0.001`、`crop_quantile=0.95`（IoU 0.725 → 0.750）。

**社区参考**：[3DGS-to-PC](https://arxiv.org/abs/2501.07478) 走的是另一条路 ——
从每个高斯按其三维密度函数**概率采样**点，并用 **Mahalanobis 距离**阈值剔除极端离群点。
这比"只取高斯中心"或"只用深度反投影"都更贴合"高斯是密度函数"的本质，列为后续选项。

### G32.【重要·已修复】PSNR 周期性骤降是**度量混叠**，不是训练不稳
现象：真实数据训练时 PSNR 曲线在**固定步数**反复骤降，看起来像训练崩了：

```
step 6000  PSNR=13.13
step 12000 PSNR=16.66
```

而且**内置密度控制和官方 `DefaultStrategy` 都在同样步数降** —— 这就说明问题不在训练。

**根因（很隐蔽）**：训练视图是按**循环**取的
```python
idx = train_idx[step % len(train_idx)]      # 行 615
```
而评估间隔与循环长度**不互质**。本机实测 `len(train_idx)=110`、`eval_interval=1000`：
```
1000 % 110 = 10
6000 % 110 = 60
12000 % 110 = 60      <-- 与 6000 落在循环里的**同一相位**
```
即两次评估看到的是**循环里的同一张"难图"**，而且每 11 次评估（11000 步）完整重复一次。

**对策**：把"日志用的评估"与"最终可信指标"分开 ——
* 中途评估固定用**前 3 个留出视图**（确定性，不再与训练循环混叠）
* 最后一次评估用**全部 12 个留出视图**（作为最终可信数字）
新增 `train.eval_quick_views`（默认 3）。

**修完之后的收获**：曲线不再有假骤降，于是**看到了真实趋势** ——
模型峰值在 4000~8000 步，之后**确实在退化**（官方策略最终全留出集只有 17.85 dB）。
这个结论在混叠存在时是**看不出来**的。

> 教训：**测不准的时候先怀疑度量，再怀疑模型**。
> 一处"周期性、和配置无关"的异常，通常指向采样/循环的相位关系，而不是模型本身。

### G33.【已实现】整体复用官方 `DefaultStrategy`（不再零散抄公式）
G31 记录了"零散移植官方 grad2d 统计量三次都失败"。这一轮换了正确做法：
**直接复用官方类**（含 `gsplat/strategy/ops.py` 的
`duplicate/split/remove/reset_opa` 与 `grad2d/count` 统计量），
而不是自己重写其中几处。

接入方式（新增 `train.densify_strategy=builtin|official`）：
```python
from gsplat import DefaultStrategy
gs_strategy = DefaultStrategy(
    prune_opa=..., grow_grad2d=cfg.densify_grad_threshold,
    grow_scale3d=..., prune_scale3d=...,
    refine_start_iter=cfg.densify_from, refine_stop_iter=cfg.densify_until,
    reset_every=cfg.opacity_reset_interval, refine_every=cfg.densify_interval,
    pause_refine_after_reset=..., key_for_gradient="means2d")
gs_strategy.check_sanity(params, optimizers)      # 参数/优化器字典结构已符合其约定
gs_state = gs_strategy.initialize_state(scene_scale=scene_scale)
# 循环内：
gs_strategy.step_pre_backward(params, optimizers, gs_state, step, info)   # backward 前
loss.backward(); optimizer.step(); optimizer.zero_grad()
gs_strategy.step_post_backward(params, optimizers, gs_state, step, info)  # grow->prune->reset
```

**一次性探针验证**（`scripts/probe_official_strategy.py`）：`check_sanity` 通过、
`state` 键为 `['grad2d','count','scene_scale']`、400 步无崩溃 ——
证明**可以直接接上，不必重写**。这正是 G31 结论的落实：
"要真正对齐官方，应整体复用而不是零散补"。

> 注：`DefaultStrategy` 在**单视图/步**的训练模式下与官方（多视图/步）行为不同，
> 实测其最终质量低于本项目实测校准的内置实现（17.85 vs 26 dB 级）。
> 所以官方策略作为**可选项**提供（`densify_strategy=official`），
> 默认仍是内置实现 —— 这是实测结论，不是偏好。

### G34.【严重·已修复】检查点保存被"不透明度重置"污染 —— 导出的 PLY 渲染一片黑
这是本项目影响面最广的一个 bug：**所有下游产物（预览、网格、贴图、质量指标）
都从 PLY 读模型**，而这个 PLY 一度是坏的。

**现象**：训练日志说 22~24 dB，但从 PLY 渲染出来**一片黑**，
逐视图 PSNR 只有 ~10 dB（我用 `diag_checkpoint_views.py` 逐视图验证时发现）。

**根因（顺序 bug）**：不透明度重置把 logit 不透明度钳到
`logit(prune_opa*2)` = `logit(0.01)`。而 step 15000 **同时**满足
`15000 % 3000 == 0`（重置步）与"最后一步"。原来的循环顺序是
**【重置 → 评估 → 保存】**，于是"最终检查点"存下的就是**刚被重置完的状态**：

```
iteration_2000   sigmoid后 p50=0.10306  max=1.00000     ← 正常
iteration_10000  sigmoid后 p50=0.01814  max=0.28997     ← 开始塌
iteration_15000  sigmoid后 p50=0.01000  max=0.01000     ← 塌陷，90.6% 被钉在 0.01
```

**修法**：
1. 把"不透明度重置"**整体后移**到"保存检查点 + 评估"之后（循环末尾）
2. **最后一步跳过重置** —— 最后一步重置没有任何恢复机会，只会让最终快照变差

**修复效果（同一份数据、同一配置）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| iteration_15000 不透明度 max | 0.01（塌陷） | 0.10687 |
| "全为 0.01" 的比例 | 0.906 | 0.001 |
| PSNR 曲线（3 固定视图） | 6000/12000 骤降到 10~13 | 21.5 → 25.5 **平滑单调** |
| 最终全留出集（12 视图） | 14.41 dB | **25.55 dB** |

**顺带推翻了我之前的一个误判**：我曾把 PSNR 周期性骤降解释为
"评估视图混叠"（G32）。改用固定 3 个视图后低谷依然在同样步数 ⇒
**混叠不是主因**，真正原因就是本条（PLY 坏快照）。
（`train.eval_quick_views` 这个改动仍然保留 —— 它让日志更可比。）

> **定位方法（值得复用）**：当"训练器说好、下游说坏"时，
> **去查两者之间的落盘/读盘环节**。具体三步：
> ① 逐检查点、逐视图独立算 PSNR，与训练器报的数字对比（发现矛盾）；
> ② 存"渲染｜真值"并排图**肉眼看**（确认是黑的，而不是几何偏移）；
> ③ 用 `plyfile` 直接读**原始字段**（看到 `opacity max = -4.59512 = logit(0.01)` 即锁定）。
> 新增工具：`scripts/diag_checkpoint_views.py`、`scripts/diag_read_ply.py`。

### G37. 提高抽帧密度要**同步提高迭代数**，否则每帧覆盖反被稀释
用户要求"增加数据"。做法：把 IMG2 的抽帧从 122 张提到 **242 张**，
同时**不再放大到 1920**、保持**原生 720×720**。

**为什么不该放大**：源视频真实分辨率只有 720×720（0.52 MP），
而原流程按 `frames.long_side=1920` 把它插值放大到 1920×1920（3.69 MP）——
**像素多了 7 倍，信息一点没多**，还让训练、分割、导出全都变慢。
`frames.long_side=0` 可跳过缩放。

**效果（位姿显著变好）**：

| 指标 | img2-01（122 帧 / 放大 1920） | img2-02（242 帧 / 原生 720） |
|---|---|---|
| COLMAP 注册率 | 122/122 | **242/242** |
| 平均重投影误差 | 1.212 px | **0.912 px（改善 25%）** |
| 稀疏点 | 46,262 | 37,913 |
| 训练 PSNR（全留出集） | 20.23 dB | **20.00 dB（持平）** |
| 高斯数 | 194,673 | 139,235 |

**位姿准了 25%，PSNR 却没涨 —— 这是本轮最值得记的一点**：

原因不在位姿，而在**每帧被"看"到的次数被稀释了**：

| 作业 | 帧数 | 迭代 | 每帧覆盖 ≈ 迭代/帧数 |
|---|---|---|---|
| img2-01 | 122 | 15000 | **123 次** |
| img2-02 | 242 | 15000 | **62 次**（只有一半）|

而且 3 视图的 PSNR 曲线到 step 14000 **还在上升**（14.33 → 14.75），
说明**模型没训完**，不是位姿不到位。

> **结论（可迁移）**：**抽帧密度与迭代数要一起调**。
> 粗略经验：让 `iterations / 帧数` 保持在 **100~300** 这个量级。
> 只加帧数不加迭代，等于把每帧的学习次数砍半 —— 位姿会变准（COLMAP 用的是帧间几何，
> 帧多自然更准），但辐射场反而更欠拟合。
> 已在 `docs/02-操作手册.md` 与配置注释里写明这条配比关系。

（后续验证：`img2-03` 用同样 242 帧但把迭代提到 35000，看是否追平/超过 20.23 dB。）

### G38.【严重·已修复】COLMAP 多模型时无条件选 `sparse/0`，把好模型丢掉
**症状**：同一份输入、同一套参数，242 帧的作业报出**注册率 0.8%（2/242）**，
而且**可稳定复现**（重跑两次都是 2/242）。但 COLMAP 日志里明明写着：

```
Registering image #169 (num_reg_frames=241)
Keeping successful reconstruction
```

即 **COLMAP 实际注册了 241 帧** —— 说明问题在**我们这边**。

**根因**（一眼可辨的低级 bug）：
```python
def _find_model(self, sparse: Path) -> Path | None:
    if (sparse / "0").exists():
        return sparse / "0"        # ← 无条件返回！
    subs = [...]
    return max(subs, key=score)    # ← 这段永远执行不到
```

COLMAP 的 `mapper` 行为是：先把第一个重建写进 `sparse/0`，随后用其它初始种子对
继续重建，写进 `sparse/1`、`sparse/2`…，**并且最后会把最优重建另存为一个新编号**。
所以 `sparse/0` 经常是**最小的那个**。（关掉 `Mapper.multiple_models` 并不能
阻止多编号输出 —— 那是"是否继续找更多模型"，不是"写到哪个目录"。）

实测三个模型的实际大小：

| 目录 | images.bin | points3D.bin |
|---|---|---|
| `sparse/0` | 143,908 B（2 图）| 20,644 B |
| `sparse/1` | 112,708 B | 5,636 B |
| **`sparse/2`** | **12,195,484 B（241 图）** | **4,955,679 B** |

**为什么之前一直没暴露**：`img2-02`（同样 242 帧）**只产出了一个模型**，
`sparse/0` 恰好就是最好的那个 —— 纯属侥幸。`img2-03` 才触发。

**修法**：`_find_model` 改为**扫描所有子目录、按 `images.bin` 体积取最大**；
全为 0（没有任何 `images.bin`）时返回 `None`。
（用文件体积而不是解析二进制，够用且不用引入解析开销。）

**验证**：修复后重跑 COLMAP —— **注册率 100.0%（242/242），重投影 0.905px，
稀疏点 38,129**（修复前是 2/242、308 点）。

**回归测试**：`tests/test_colmap_io.py::test_colmap_stage_picks_largest_sparse_model`
用 3 个不同体积的假模型断言必须选最大的那个，并覆盖"只有一个模型"与
"没有任何 images.bin"两种情况。测试数 **32 → 33**。

> 教训：**当一个失败"可稳定复现"、但底层工具的日志显示它成功了**，
> 就该立刻怀疑**我们读取/选择结果的那段代码**，而不是继续怀疑工具或数据。
> 我一开始把它当成"COLMAP 随机失败"，还准备重跑几次碰运气 —— 那是错的方向。

### G40. 网格"白 + 杂乱尖锐"的根因：**导出没有法线 + 查看器光照是常数**
用户反馈"模型网格是白的、网络依然杂乱尖锐"。逐项查证的结果与直觉相反：

**① 网格不是白的 —— 数据是暗灰的**
导出网格的顶点色统计：`img2-04` RGB 均值 **0.264**、`img2-reg` **0.255**，
`>0.9 的像素占比 = 0.000`。所以"白"**不是顶点色的问题**，而是**渲染出来**的效果。

**② 真正的根因是两个缺陷叠加**
* **导出的网格 GLB 没有 `NORMAL` 属性**（只有 `POSITION` + `COLOR_0`）。
  glTF 规范下没有法线就是**逐面平面着色** ⇒ 每个三角形亮度单独跳变 ⇒
  看起来"碎、乱、尖锐"，而模型本身没这么糟。
* **我们自己的查看器光照是常数**。原片元着色器写的是
  ```glsl
  float lam = 0.55 + 0.45 * max(dot(normalize(uLight), vec3(0,0,1)), 0.0);
  ```
  两个方向都与像素无关 ⇒ 全屏同一个值 ⇒ **等于完全没有光照**。
  而且它**从来没接收过法线**。所以"给 GLB 加 NORMAL"对 GUI 也无效，必须两头一起改。

**修法**：导出侧写 `NORMAL`（顶点法线，y/z 随坐标翻转一起取反）；
查看器侧新增 `aNrm` 属性 + 逐像素半兰伯特光照，没有法线时才退回固定方向。

**③ 量化验证**（邻域法线一致性 = 相邻顶点法线点积均值，越大越平滑）
| 模型 | 法线径向一致 | **邻域法线一致** |
|---|---|---|
| img2-04（无正则） | 0.0058 | **0.0174** |
| img2-reg（开正则） | −0.0290 | **0.0820（4.7 倍）** |

> 注：**"法线径向一致"（与"顶点→质心"同向）对平面结构不适用** ——
> 牌楼是大片平面，径向近似为 0 属正常，不能据此判"法线乱"。
> 判断平滑度要看**邻域一致性**。

### G41. 采纳 Faster-GS / 3DGS-MCMC 的正则项：能减少 25% 高斯，但 PSNR 略降
参考用户给的 [Faster-GS](https://github.com/nerficg-project/faster-gaussian-splatting)
（CVPR'26，其 README 也指向 [AbsGS](https://ty424.github.io/AbsGS.github.io/) 与
[Gaussian Opacity Fields](https://niujinshuchong.github.io/gaussian-opacity-fields/)），
采纳了三项：

| 项 | Faster-GS 取值 | 我们加的配置 | 作用 |
|---|---|---|---|
| 不透明度 L1 正则 | 0.01（配 MCMC）| `train.opacity_reg` | 让"开着但不贡献像素"的浮点被优化掉 |
| 尺度 L1 正则 | 0.01 | `train.scale_reg` | 抑制个别高斯长到过大 |
| 训练后最小不透明度 | `1/255 ≈ 0.0039` | `train.min_opacity_final` | 收尾删掉几乎不可见的高斯 |

**实测（IMG2，242 帧 / 35000 迭代）**：

| 配置 | 高斯数 | PSNR（24 视图留出）| 邻域法线一致 |
|---|---|---|---|
| 基线 | 127,850 | **21.17 dB** | 0.0174 |
| 正则 0.01 + 收尾清理 | **95,604（−25%）** | 20.63 dB（−0.54）| **0.0820（4.7×）** |

**结论：正则不是提升 PSNR 的手段，而是清理产物的手段。**
它把高斯数减了 25%、法线一致性提升 4.7 倍（观感更干净），代价是 PSNR 略降。
所以三个开关**默认保持 0**（不改变既有行为），需要"更干净的产物"时显式打开。

### G42.【严重·已修复】反投影用的是**视线方向**当法线，不是表面法线
用户反馈"`model_mesh.glb` 看不了、网格杂乱尖锐"。排查链条（每一步都有实测证据）：

1. **文件与传输都正常**：HTTP 200、`magic=glTF`、1613324 字节、无压缩编码
2. **解析正常**：Node 能解出 24273 顶点 / 79724 三角形，索引无越界
3. **取景正常**：100% 顶点落在视口内，深度在 near/far 之间
4. **顶点色不是白的**：均值 0.262（暗灰），`>0.9` 占比 0
5. **法线朝向也正常**：与"质心→顶点"点积 0.005、与面法线 0.30 一致
6. 最后**用查看器同样的相机与光照模型在 CPU 上把 GLB 光栅化出来**，
   得到一张图：**不是黑的，是碎片化的薄面**（只覆盖 8% 像素）。
   ⇒ 结论："看不了"的真实含义是**网格本身是碎的**，查看器没坏。

**根因**（`mesh_export.backproject_depth_to_points`）：
```python
cam_n = cam_pts / np.linalg.norm(cam_pts, axis=1, keepdims=True)   # ← 错
```
这是**视线方向（相机→像素的射线）**，不是表面法线。它不是"穿过表面继续往外"，
而且**同一表面点从不同视角看方向完全相反**（正面朝你、背面背你）。
泊松重建正是靠法线定朝向 —— 喂这种法线时指示函数无解，输出"填满轮廓的碎面"：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 轮廓 IoU | 0.837（轮廓本来就对）| — |
| **邻域法线一致** | **0.0022** | **0.0655（提升 30 倍）** |
| 法线翻转比例 | 50.0% | 45.9% |

**修法**（社区标准，2DGS / Gaussian Opacity Fields 同源）：**从深度图的梯度求表面法线**
```python
# 深度图 z(u,v) -> 相机系点 (x,y,z)；切向量
tu = [zu*x/fx + x*zu/z + z, zu*y/fy, zu]
tv = [zv*x/fx, zv*y/fy + y*zv/z + z, 1]
n  = normalize(cross(tv, tu))     # zu/zv 为深度对像素的偏导（中心差分）
```
外加**背面剔除**（法线与视线同向的像素才可信）和**统一朝向相机**
（否则多视角重叠处的相反法线会在体素下采样里互相抵消成 ~0）。
同时把泊松的 `orient=True` 改为 `False` —— 那一步是给**无朝向**点云用的，
在有正确法线时反而打乱它们而且慢。

### G43.【未解决·已定位】不透明度在训练后期持续塌陷，导致深度失效、网格成碎片
修复 G42 后网格**仍不够好**，继续追查发现更上游的问题。

**症状**：`img2-04` 保存的各检查点不透明度中位数一直在降
（step 25000→35000：0.0165 → 0.0148 → 0.0185 → **0.0124** → 0.0138），
最终 **`>0.02` 的高斯只占 0.2%**。也就是说模型变成"**一大团极低不透明度的薄雾**"：
大量半透明高斯叠加后轮廓仍能填满（所以 **PSNR 21.17 dB、轮廓 IoU 0.837 都正常**），
但**深度是完全模糊的** ⇒ 反投影点云不可信 ⇒ 泊松只能给出碎片。

这解释了一个一直矛盾的组合：**指标正常、观感很差**。
（PNR/IoU 这类"轮廓级"指标对"薄雾式退化"不敏感。）

**已排除**：`opacity_reset_interval = 0`（已确认生效，且 G39 修过默认值漂移）。
**所以是训练动力学里别的东西在压低不透明度** —— 这是**下一个要查的问题**。

**建议排查方向**（按可能性排序）：
1. 不透明度学习率（我们 0.05，Faster-GS 用 0.025 —— 我们快一倍）
2. `mask_loss_until=1.0` 使掩码外的高斯**完全不参与损失**，可能被优化器推向低不透明度
3. `densify_until=4000` 偏早：之后不再加密，模型转向"摊薄"已有高斯来降损失
4. 缺少不透明度正则/上限约束，缺少 3D filter（Speedy-Splat）

**判据建议**：以后评估重建质量时**必须同时看"不透明度分布"**，
不能只看 PSNR 与 IoU —— 这次就是这两个指标把"薄雾退化"完全掩盖了。

### G44.【严重·已修复】`ctx.cfg(k, d) or d` 把合法的 0 吞掉 —— 我前两轮的"修复"从未生效
这是 G43 那个"不透明度持续塌陷、但查不出原因"的**真正答案**。

**症状**：配置里明确写了 `opacity_reset_interval = 0`（关闭不透明度重置），
但训练仍然每 3000 步重置一次，末次重置状态被存成最终检查点。

**根因**：`GsplatBackend` 用**手写的一长串**参数构造 `TrainConfig`：
```python
opacity_reset_interval=int(ctx.cfg("opacity_reset_interval", 3000) or 3000)
#                        ctx.cfg(...) 返回 0  ->  0 or 3000 = 3000  ->  又是 3000！
```
`or` 把 `0` 当假值。于是"已关闭重置"这个修复**每一轮都写了、每一轮都没生效**。

**为什么前两轮没发现（我自己的排查错误）**：默认值在这个项目里有**三处**来源：
1. `config.py` 的 `DEFAULTS["train"]`（G39 修过）
2. `TrainConfig` dataclass 字段默认值（G39 修过）
3. **`GsplatBackend` 里手写的 `or 默认值`（这一处当时没查）**

我修完前两处就宣布"已关闭重置"，还写了测试断言 `DEFAULTS["train"]["opacity_reset_interval"] == 0`
—— **测试通过，但运行时用的是第三处**。教训：**"改了默认值"必须验证到"运行时对象的值"**，
中间任何一层转换（尤其是 `or`、`get(k, d) or d`、`int(x or y)`）都可能把它吃掉。

**同一处的第二个隐患**：手写注入只覆盖了 **19/36** 个字段，
`opacity_reg` / `scale_reg` / `min_opacity_final` / `lr_opacities` / `ssim_weight` /
`eval_interval` / `white_background` 等**改配置完全不生效且不报错**。

**修法**：
* `_build_cfg()` 改为**按 `dataclasses.fields(TrainConfig)` 循环注入**，用 `None` 作哨兵只判断
  "键是否存在"，再按字段声明类型转换。新增字段无需再改这里。
* 新增 `StageContext.cfgt(key, default, cast)` 作为**受认可的类型化读取方法**，
  它不使用 `or`，因此保留合法的 `0` / `False`。
* 不透明度学习率 `5e-2 -> 2.5e-2`（官方 0.05 是**配合定期重置**才成立的；
  关闭重置后 0.05 会把不透明度一路压向 0。Faster-GS / 3DGS-MCMC 都用 0.025）。

**验证（修复前后对比，同一素材 242 帧 / 35000 迭代）**：

| 检查点 | img2-04（修复前）| img2-opfix（修复后）|
|---|---|---|
| iteration_10000 | p50 0.0271 | p50 0.1000 |
| iteration_15000 | p50 0.0355 | p50 0.1097（仍在升）|
| iteration_35000 | **p50 0.0138（塌陷）** | **p50 0.1205（8.7 倍）** |
| `>0.02` 占比 | **0.2%** | **87.2%** |
| 可见高斯 | 238 | 150,237 |
| 3 视图 PSNR 曲线 | 抖动、周期下陷 | **单调平滑上升** |
| 最终 PSNR | 21.17 dB | **21.23 dB** |

**最重要的变化是渲染**：修复前是一团白雾（牌楼结构完全看不出），
修复后**柱子、拱门、屋顶脊饰、"文昌坊"匾额都清晰可辨**。

> 教训（可迁移）：**当"我明明改了默认值却没生效"时，先搜索所有 `cfg(...) or 默认值` 形态**。
> 本项目共有 61 处 `ctx.cfg(...) or ...`，已提供 `cfgt()` 作为正解，并把 export 阶段的
> `mesh_depth_stride` 等改为 `cfgt`（原来它也无法配成 0）。

### G45. 查看器万向锁：pitch 硬夹 ±1.5 rad + lookAt 共线退化
用户反馈"查看器的视角旋转转到一个方向后转不了了"。

**两个叠加原因**：
1. `pitch = Math.max(-1.5, Math.min(1.5, ...))` —— 硬夹在 ±86°，竖直方向被锁死。
2. 更根本的是 `m4lookAt` 的共线退化：相机方向与 `up=(0,1,0)` 共线（正上/正下俯视）时
   `cross(up, z)` 是零向量，而 `norm()` 的兜底是 `|| 1` ⇒ 得到 `[0,0,0]`
   ⇒ **整个视图矩阵含 NaN ⇒ 画面消失**。

**修法**：pitch 上限改为 `π/2 - 1e-4`；`m4lookAt` 检测退化后换一个不平行的参考轴；
拖拽加指针捕获（拖出画布不丢事件）；补单指触摸旋转。

**验证**：`scripts/probe_viewer_runtime.mjs` 在 Node 里加载**真实 viewer.js**
（stub WebGL/DOM）并模拟连续拖过顶/底，采样 18 次 MVP 矩阵，**0 次含 NaN**。
该探针已接入 pytest（`tests/test_viewer_frontend.py`），并有静态检查禁止 `±1.5` 夹取回归。

**顺带修掉的线框 bug**：原先 `drawElements(gl.LINES, 三角形索引数)`，
索引数（239172）不是偶数 ⇒ WebGL 报 `INVALID_OPERATION` ⇒ **整帧什么都不画**。
现在为线框单独生成线段索引（478344，偶数）。

### G46. 泊松 `depth=10` 在本机（15 GB 内存）不可行：平滑阶段要跑 1 小时以上
用户早前提过"可试泊松 depth=10"。实测结论：**在 242 帧、530 万输入点的规模下不可行**。

| 配置 | 泊松输出 | 后果 |
|---|---|---|
| `depth=9`（默认）| 485 万三角形 / 252 万顶点 | ✅ 全程约 2.5 分钟 |
| `depth=10` + `voxel_div=600` | **2771 万三角形 / 1393 万顶点** | ❌ 卡在"平滑（taubin × 5）"**超过 61 分钟**，内存 7.9 GB |

`depth` 是八叉树的深度，每 +1 分辨率翻倍、三角形约 ×5.7。而**平滑/QEM 这些后处理是
CPU 上对全体顶点/三角形做迭代**，规模上去后耗时非线性增长。
本机只有 15.2 GB 内存，1393 万顶点光位置数据就 ~334 MB，加上邻接结构会到 GB 级。

**工程结论**：
* 本机（15 GB 内存）**泊松 depth 保持 9**；想用 10 必须先**大幅减少输入点**
  （提高 `mesh_depth_stride`、收紧 `mesh_crop_quantile`），而不是直接调 depth。
* 若要支持 depth=10，需要把"平滑 + QEM"的顺序调整为**先 QEM 降到目标面数再平滑**，
  或者只对抽样后的网格做平滑 —— 目前是"先平滑全体、再 QEM"，在大网格上代价极高。
* 已记入待改进：`mesh_smooth_iters` 在大网格上应自动降级或跳过。

### G47. 后处理顺序修好后，`depth=10` 仍不可行 —— 瓶颈是"点数 × depth"，不是顺序
G46 记录过"`depth=10` 卡在平滑 61 分钟"。本轮把顺序改成 `预简化 -> 平滑 -> 最终 QEM`
（并加了测试），**顺序问题确实修好了** —— 日志现在会先打印预简化。
但实测发现 **`depth=10` 依然不可用**，只是卡的位置换了：

| 阶段 | depth=10 实测 |
|---|---|
| 反投影点数 | 530 万（`voxel_div=600`）|
| 泊松输出 | **2771 万三角形 / 1393 万顶点** |
| 预简化（QEM 降到 80 万）| **运行 27 分钟仍未完成**，内存 8.9 GB |
| 旧顺序的平滑 | 运行 61 分钟仍未完成 |

**结论修正**：`depth=10` 在 530 万点输入下产出 2771 万面，
**而"把 2771 万面做任何全局处理（QEM 或平滑）"本身就超出了本机能力**。
换顺序只是把瓶颈从平滑挪到 QEM，并没有消除它。

**真正的杠杆是减少输入点数**，因为泊松输出规模 ≈ f(点数, depth)：

* 想让 `depth=10` 可用，必须先把输入点降到**几十万级**
  （调大 `mesh_depth_stride`、调小 `mesh_voxel_div`、收紧 `mesh_crop_quantile`），
  而不是直接调 `depth`。
* 本机（15.2 GB 内存 / Ryzen 9 7945HX）的实用配置：**`depth=9`**，
  输入 530 万点 → 485 万面 → 全流程 **2.5 分钟**。

> 教训：**"换顺序"只能重排瓶颈、不能消除瓶颈**。在改算法顺序之前，
> 先算清楚"数据规模 × 每阶段的复杂度"，否则会像这次一样把一个 27 分钟的坑
> 从 A 阶段搬到 B 阶段。已在配置注释里写明 `depth` 与点数的关系。

### G48. `mesh_min_alpha` 阈值**不能全局调高** —— 单素材调优会被另一素材推翻
背景：网格表面仍显碎屑。怀疑是"深度图上不可信的低不透明度像素混进了反投影点"，
于是试把 `mesh_min_alpha` 从 0.5 提到 0.7（只保留更可靠的不透明像素）。

**单看 IMG2（牌楼）结论很好**：

| 配置 | 邻域法线一致 | 翻转比例 | IoU |
|---|---|---|---|
| `min_alpha=0.5`（默认）| 0.1019 | 44.0% | **0.840** |
| **`min_alpha=0.7`** | **0.1764（+73%）** | 39.4% | 0.815 |
| `min_alpha=0.7` + `trim_sigma=1.5` | 0.4593（+350%）| 22.2% | 0.744 |

看起来"0.7 是纯收益"（法线 +73%、IoU 只 −0.025）。**但换到另一个素材就反了**：

| 数据集 | `min_alpha=0.5` | `min_alpha=0.7` |
|---|---|---|
| IMG2（牌楼，242 帧）| 法线 0.1019 / IoU 0.840 | 法线 0.1764 / IoU 0.815 |
| **碗（cmp-resetfix，122 帧）**| 法线 −0.0444 / **IoU 0.910** | 法线 −0.0504 / **IoU 0.766** |

碗的 IoU **掉了 0.144** —— 这是严重回归，而且**法线一致性在碗上根本没改善**（都是负的）。

**原因**：两个场景的**高斯不透明度分布不同**。牌楼普遍较不透明（提高阈值滤掉的确实是噪声）；
碗有很多"不透明度不高但确实是必要表面"的高斯，阈值一高就把真实表面挖掉，
泊松只好去填洞，于是 IoU 崩。

**结论**：
* `mesh_min_alpha` **默认保持 0.5**，不要全局调高。
* 它是**按素材调**的参数；要提高必须**先在两份以上数据上验证 IoU 不回归**。
* 同理 `mesh_trim_sigma` 也保持 2.5（1.5 会把 IoU 拉到 0.744）。

> 教训：**单素材调参 = 过拟合到那一个场景**。本轮如果只看 IMG2，
> 我会把 `min_alpha` 默认改成 0.7 并宣称"法线一致性提升 73%"，
> 实际却让另一个素材的 IoU 崩掉 0.144。
> 凡是要改**默认值**，至少要在两份差异明显的数据上跑通对比。

### G50. `densify_until` 实测：**4000 优于官方的 15000**（推翻本轮假设）
官方 [gsplat `DefaultStrategy`](https://github.com/nerfstudio-project/gsplat) 的默认是
`refine_stop_iter=15000`，而本项目用的是 4000。本轮专门做了公平对照来验证是否该改。

**先纠正一个前提**：查证发现我们与官方的**唯一偏离**就是这个值 —— 其余全部一致：

| 参数 | 官方 | 我们 |
|---|---|---|
| `refine_start_iter` | 500 | 500 ✅ |
| **`refine_stop_iter`** | **15000** | **4000** ⬅ 唯一偏离 |
| `refine_every` | 100 | 100 ✅ |
| `grow_grad2d` | 2e-4 | 2e-4 ✅ |
| `prune_opa` | 0.005 | 0.005 ✅ |
| `grow_scale3d` | 0.01 | 0.01 ✅ |
| `prune_scale3d` | 0.1 | 0.1 ✅ |

**梯度/反向传播已核对无误**：`train.densify_strategy` 默认 `builtin`，
即**直接使用官方 `DefaultStrategy`**（`key_for_gradient="means2d"`），
所以屏幕空间归一化 `grads *= width/2*n_cameras` 与 `grad2d/count.clamp_min(1)`
都由官方内部完成，不存在"抄一半"的问题。
（训练器里确实还有一条用 3D `means.grad` 的自定义路径，但**默认不启用**。）

**公平对照**（同输入、同 102/242 注册、同 10 视图留出集、都取 `iteration_35000`）：

| 指标 | `densify_until=4000` | `densify_until=15000` |
|---|---|---|
| 高斯数 | **121,284** | 431,111（**3.6 倍**）|
| PSNR | **23.96 dB** | 23.65 dB |
| **邻域法线一致** | **0.2242** | 0.0018（**差 125 倍**）|
| 法线翻转比例 | **35.1%** | 49.6% |
| 网格 IoU | 0.776 | **0.827** |
| 深度误差中位数 | **2.00%** | 2.98% |

四个指标（高斯数、PSNR、法线一致性、深度误差）一致指向 **4000 更好**；
只有轮廓 IoU 略偏向 15000，但那份网格是 112,327 面（对面 80,000，面数多 40%），
IoU 本就随面数上升，不构成"更好"的证据。

**结论**：`densify_until=4000` 保持默认。之前把它从 15000 下调到 4000 的原始理由
（"后期加密纯粹在过拟合"）在**修复不透明度塌陷之后依然成立**，
本轮用健康模型重新验证过，不是旧结论的惯性延续。

> 教训：**对齐官方 ≠ 无脑照抄官方默认值**。官方默认面向"几百~上千视图的大场景"，
> 本项目是几十~两百视图的物体环绕拍摄，加密窗口需要按视图数缩放。
> 差异必须有**公平对照**（同输入、同评估集）才能判定，见 G49 的反面教材。

### G51.【严重·已修复】深度图求法线的**切向量推导写错**，导出与训练两处都有
症状由单元测试发现：对**正对相机的平面**（深度为常数，`z_u = z_v = 0`），
算出的法线是 `[0, 0.447, -0.894]`，而正确答案是 `[0, 0, -1]` —— **偏离 26.6°**。

**错误公式**（做了 G42 的修正之后仍然写错）：
```python
tu = [zu*x/fx + x*zu/z + z, zu*y/fy, zu]
tv = [zv*x/fx, zv*y/fy + y*zv/z + z, 1]     # ← z 分量写成常数 1，错
n  = normalize(cross(tv, tu))
```

**正确推导**：参数化 `P(u,v) = z(u,v)·K⁻¹[u,v,1]`，记 `m = (x/z, y/z, 1) = K⁻¹[u,v,1]`：
```
P_u = z_u·m + z·(1/fx, 0, 0)
P_v = z_v·m + z·(0, 1/fy, 0)
n   = P_u × P_v
```
代入 `z_u = z_v = 0` 验证：`n = -z²·fx·fy·ẑ ∝ [0, 0, -1]` ✅

**为什么这个错误特别危险**：它**不退化**（长度非零），所以
既不会抛异常、也不会触发"梯度为零"的兜底，**只会静默给出偏了 26.6° 的法线**。
而它同时存在于两个地方：

| 位置 | 影响 |
|---|---|
| `mesh_export.backproject_depth_to_points` | 喂给泊松的法线整体偏斜 → 表面质量（从 G42 修好"视线当法线"之后就一直存在）|
| `trainers/gsplat_trainer.depth_to_normal` | 2DGS 法线正则的监督信号本身是错的 |

**发现方式**：写 2DGS 法线正则的单测时，用"正对相机的平面"做**可解析验证**的用例
（唯一正确答案能笔算出来），立刻暴露。若只用真实数据看指标，这个 26.6° 的偏差
会被其它噪声淹没。

> 教训：**几何公式一定要构造"能笔算出答案"的用例来测**。
> 这类错误用真实数据只能看出"质量不太好"，无法定位；
> 而"正对相机的平面 → 法线必须是 [0,0,-1]"这种断言是决定性的。

### G52. 2DGS 的两项正则**直接套到 3DGS 上是有害的**（实测负面结果）
用户要求做"2dgs 方向"。导出侧做完了（见 G42 / 2dgs 一致性投票），本轮补训练侧：
按 [2D Gaussian Splatting](https://arxiv.org/abs/2403.17888) 加**深度失真抑制**与
**法线一致性**两项正则（实现见 `two_dgs_regularizers`）。

**公平对照**（同为 200 帧 / 12000 迭代 / 700px / 同一份 IMG2，唯一差别是正则开关）：

| 指标 | 无正则（img2-2dgs-base）| 正则 0.05 / 0.1（img2-2dgs-reg）|
|---|---|---|
| PSNR | **22.15 dB** | 18.18 dB（−3.97）|
| 高斯数 | 425,744 | 201,187 |
| scale 中位数 | 0.00334 | 0.01266（**大 3.8 倍**）|
| 网格相邻面法线点积 | **0.7426** | 0.2570 |
| **法线翻转比例** | **6.5%** | **35.2%（更差 5.4 倍）**|

而且两项正则的数值**都没有下降趋势**：
```
depth : 2.37e-02 -> 2.79e-02   （变大）
normal: 3.95e-01 -> 2.99e-01   （震荡）
```
说明它们在与重建损失**对抗**，而不是在引导它。

**为什么 2DGS 能用这套权重而我们不行**（这是关键，避免后人重复试）：
2DGS 把高斯**压平成 2D 圆盘**并**显式优化法线**，"深度应集中""法线应一致"
与它的参数化是自洽的；3DGS 的椭球没有这个约束，直接加这两个损失项会与
"拟合辐射场"的目标冲突 —— 表现为尺度被撑大、几何变差。
**要真正走 2DGS 路线必须改参数化**（压平 + 显式法线），而不是只加损失项。

**处置**：两项权重**默认改为 0**（接口保留，便于换小权重或换参数化后再实验），
并在 `TrainConfig`/`config.py` 的注释里写明这次的实测数字。

> 教训：**"照抄论文的损失项"不等于"复现论文的方法"。**
> 损失项与参数化是一套的；只搬前者，后者不匹配时会得到**比不加更差**的结果。
> 本轮的方法论收获是：**先做公平对照再决定是否改默认值** —— 两步都做了，
> 所以能在把 2DGS 说成"已实现"之前发现它其实有害。

### F13. 密度控制必须照抄官方 gsplat 的"参数字典 + 迁移优化器状态"
这一处我前后错了 4 次，每次都表现为不同的报错或"静默不生效"。
**结论：不要自己发明参数扩缩容的写法，直接对齐社区成熟实现。**

官方的做法（`gsplat/strategy/ops.py:_update_param_with_optimizer` + `duplicate/split/remove`）：

```python
def param_fn(name, p):
    return torch.nn.Parameter(torch.cat([p, p[sel]]), requires_grad=p.requires_grad)

def optimizer_fn(key, v):          # Adam 的 exp_avg / exp_avg_sq 按行拼接，新增补 0
    return torch.cat([v, torch.zeros((len(sel), *v.shape[1:]), device=v.device)])

_update_param_with_optimizer(param_fn, optimizer_fn, params, optimizers)
```

即：**替换 Parameter 对象 + 迁移 optimizer.state + optimizer.param_groups[i]["params"] = [new_param]**。

我踩过的四种错法：

| # | 错法 | 现象 |
|---|---|---|
| 1 | 改 `p.data` + 重建优化器 | `Function UnsqueezeBackward0 returned an invalid gradient ... got [N_new,16,3] but expected [N_old,16,3]` |
| 2 | 把密度控制放在 `forward` 之前 | 用的是上一步梯度，判据落后一步；顺序上更脆弱 |
| 3 | 把密度控制放在 `zero_grad` **之后**却仍读 `means.grad` | `grad` 恒为 None → **一次都不加密**（高斯数从头到尾 427） |
| 4 | `copy_` 原地裁剪（重叠索引） | `The size of tensor a (481) must match tensor b (478)` |

最终正确形态（与官方 `simple_trainer.py` 一致）：

```
forward → loss.backward()
        → 缓存 grad_norm（关键：zero_grad 之后就没了）
        → optimizer.step() → optimizer.zero_grad(set_to_none=True)
        → strategy.step_post_backward()   # 我们的 densify_and_prune
```

补充：官方用的是策略自己累积的 `grad2d` 统计量（`state["grad2d"] += grads.norm(...)`），
天然不受 `zero_grad` 影响；我们为省事改成"backward 后立刻缓存范数"，效果等价。

**修好后的实测（合成数据，813x813，15000 迭代）**：
- 427 个初始稀疏点从 step 500 开始持续加密，step 15000 达到 **557,059** 个高斯，
  之后按 `densify_until` 设计停止加密；
- loss 0.2612 → **0.0187**，训练全程无报错；
- 观察：在 7 视图的合成场景上**膨胀过猛**（55 万高斯对这么小的场景明显过多）。
  官方靠 `cap_max` 与周期性 `reset_opacity` 抑制膨胀，我们已把
  `train.cap_max` 默认从 150 万下调到 **60 万**。真实数据集应重新校准这个值。
- 完整 30k 迭代在 8GB 卡上耗时约 **90 分钟**（813x813、7 视图、55 万高斯）。

**建议**：新建训练后端时，优先考虑**直接调用 `gsplat.strategy.DefaultStrategy`**
（它把 initialize_state / step_pre_backward / step_post_backward / check_sanity 都封装好了），
而不是自己实现密度控制。本项目保留自研实现是为了不绑定 gsplat 内部 API，
但代价就是上面这 4 个坑——这是一次很值的教训。

## G. 训练算法与架构复盘

### G1.【架构级复盘·用户点出的本质】"参数变了，优化器不会自己跟上"
> 这一节是用户点出来的，比我自己总结的"4 种错法"更接近本质。

**现象层**：密度控制改了参数形状后，训练要么报
`... returned an invalid gradient ... expected shape compatible with [N_old]`，
要么静默不加密，要么张量尺寸对不上。

**本质层**：PyTorch 里**优化器与参数是"显式绑定"关系**，不是"自动跟随"：

| 对象 | 绑定方式 | 参数被替换后会怎样 |
|---|---|---|
| `optimizer.param_groups[i]["params"]` | 存的是 `Parameter` 的**对象引用** | 仍指向旧对象 → 更新的是已不参与前向的张量 |
| `optimizer.state[param]` | **以 Parameter 对象为字典 key** | 新参数查不到 state → Adam 动量/二阶矩**静默丢失**（不报错） |
| autograd 图 | 节点持有前向时用到的**张量** | 形状变了但图没重建 → backward 形状校验失败 |

所以社区实现（gsplat `strategy/ops.py`）必须手写 `_update_param_with_optimizer`：
**新建 Parameter 对象 + 把 state 按同样规则变换后挂到新对象 + 改写 param_groups**。
这不是技巧，而是这套 API 的必然要求。

**我犯的错一句话概括**：我按"自动跟踪"的直觉写（改 `p.data`、重建优化器、手动清 grad），
而这套 API 是"显式绑定 + 显式迁移"的语义 —— 方向错了，怎么试都不对。

**连带第二个坑**：判据与生命周期不同步。官方顺序是
`optimizer.step() → zero_grad(set_to_none=True) → 密度控制`，
而 `zero_grad` 之后 `means.grad` 就是 `None`。
官方策略因此**自己累积**统计量（`state["grad2d"] += grads.norm(...)`），
我一开始直接读 `means.grad` → 恒为 `None` → 一次都不加密。
最终改为"backward 之后立刻缓存 grad_norm"，效果等价。

**方法论教训**：
1. 陌生领域不要逐点试参数。先找**成熟实现的对应代码段**，对齐它的调用顺序与不变量，
   再回头比对差异。
2. 本次弯路代价很大（用户陪看 7 小时，我试了 4 轮才转向查资料）。
   本机 `raw.githubusercontent.com` 不通，但 `cdn.jsdelivr.net` 可用：
   `https://cdn.jsdelivr.net/gh/nerfstudio-project/gsplat@main/gsplat/strategy/ops.py`，
   用 Python `urllib` 下载（`web_fetch` 会因 content-type 被拒）。
3. 对"参数会变形状"的训练循环，**默认假设优化器不会自动跟随**：
   要么显式迁移，要么直接用官方策略类
   （`gsplat.strategy.DefaultStrategy` 已封装 initialize_state /
   step_pre_backward / step_post_backward / check_sanity）。

### G3.【已修复】ctx.cfg 的配置回退写错 → config.toml 的 [train] 段从未生效
- **现象**：`--set train.iterations=800` 完全不起作用，训练照样跑 30000 步；不报任何错。
- **原因**：两处叠加。
  1. `StageContext.cfg()` 的回退是 `settings.get(key)`，而 config.toml 是**嵌套**的
     （`[train] iterations` → 点路径 `train.iterations`），
     于是阶段里的 `ctx.cfg("iterations", 30000)` **永远取不到配置**，静默用默认值。
  2. 顺带发现：整个 `[train]` 段（迭代数、分辨率、密度控制参数）都是这个情况，
     也就是说**配置文件里的训练参数从来没被读过**。
- **修法**：裸键先拼当前阶段成点路径再回退（`train.iterations`），点路径写法仍直接生效；
  新增 `_MISSING` 哨兵以区分"键不存在"与"值为 None"。
- **验证**：`--set train.iterations=800` → 日志 `迭代 800`，800 步精确结束；
  无 `--set` 时能从 config.toml 读到 30000。
- **教训**：**"配置项不生效"比"配置项报错"危险得多**。
  凡是"默认值恰好合理"的静默回退，都可能在很长时间里不被发现。
  新增配置项时应顺手加一条"改它 → 行为确实变化"的验证。

### G4.【已修复·发散根因】密度控制漏了官方的"尺度裁剪"
- **量化证据**（修复前）：
  | 迭代 | 高斯数 | log尺度 max | 坐标范围 |
  |---|---|---|---|
  | 5000 | 37,158 | 41 | 125 |
  | 15000 | 557,059 | 332 | 215 |
  | 30000 | 557,059 | **739**（exp 溢出） | 215 |
  相机环绕半径仅约 3.6，坐标范围却到 215 → 高斯全飞出视锥，预览只剩原点附近一小撮。
- **根因**：官方 `DefaultStrategy._prune_gs` 有**两条**裁剪，我只实现了第一条：
  ```python
  is_prune   = sigmoid(opacities) < prune_opa                        # 0.005，已实现
  if step > reset_every:
      is_too_big = exp(scales).max(-1) > prune_scale3d * scene_scale  # 0.1，漏了
      is_prune |= is_too_big
  ```
  缺第二条 → 尺度无上界 → 分裂时 `offset = randn * 2*exp(scales)` 跟着爆炸。
- **同时纠正的第二个错误**：分裂/克隆的分界我原来用"当前尺度中位数"作参照，
  而每次分裂又把尺度除以 1.6 → 中位数下降 → 阈值自增强 → 无界分裂。
  官方用的是**绝对阈值** `grow_scale3d * scene_scale`（0.01），
  其中 `scene_scale` 由相机位置**一次性**估出。
- **修法**（全部对齐官方语义）：
  - `scene_scale` = 相机中心到其均值的平均距离（官方 `initialize_state` 同款）；
  - `grow_scale3d=0.01`：尺度 ≤ 0.01×scene_scale 走克隆，否则分裂；
  - `prune_scale3d=0.1`：尺度 > 0.1×scene_scale 直接裁剪（仅在 step > 3000 后启用）；
  - `revised_opacity=0.1`：分裂出的高斯不透明度调低（官方做法）。
- **验证**：尺度 max 从 25.99（发散中）被**精确**夹到 `0.2952 = 0.1 × scene_scale(2.9526)`；
  坐标范围 215 → 3.82（与 scene_scale 同量级）；30k 迭代耗时 90min → 34min。
- **教训**：对齐社区实现时要**逐条核对它做了哪些约束**。
  每条 prune / clamp / reset 都是防发散的，只对齐主流程等于没有对齐。
  这次属于"实现了官方的部分逻辑"，比完全没实现更难发现。

### G5.【已修复】PSNR 恒为 0（两个原因叠加，都不是渲染坏了）
- **现象**：训练日志 `评估 PSNR=0.00 dB`，但 loss 明明在下降。
- **原因一（调用层）**：调用 `evaluate(...)` 时少传参数导致整体错位
  （`opacities` 落到 `scales`、`background` 落到 `masks`），
  而各张量形状恰好兼容 → **不报错**，只是结果无意义。
- **原因二（评估集为空）**：`n_eval = ... if len(imgs) >= 10 else 0`，
  7 个视图时评估集为空 → `evaluate` 直接返回 `0.0`。
- **解法**：
  1. 改为**全部关键字传参**；`save_ply` 同样改为关键字传参（同类隐患）。
  2. 视图不足时**不留评估集**（留出 10% 会削弱小数据集训练），
     改为在训练视图上算 PSNR，并在日志与 metrics 里标注
     `psnr_on_train` / `psnr_views`，避免误读为泛化指标。
  3. 顺带新增诊断：训练结束时把 "渲染 | 真值 | 差异" 并排写到
     `04_train/diagnostics/render_vs_gt/`，用于肉眼确认位姿是否对齐。
- **验证**：PSNR 现在有真实数值（step 8000 达 **35.99 dB**），
  这同时**反证了相机位姿约定正确**（若轴翻转写错，PSNR 会在 8~10 dB 附近）。
- **教训**：多个同类型（都是 Tensor）的位置参数，顺序一错就是静默错误；
  对外函数调用尽量用关键字。

### F11.【误报自查】make_shortcuts 报告"已创建"但实际没有

- **现象**：脚本连续两次输出"已创建: C:\Users\admin\Desktop\gsflow Web GUI.lnk"，但文件不存在。
- **原因**：`WScript.Shell.Save()` 失败时 PowerShell 的**退出码仍是 0**，而脚本里的

- **教训**：凡是"调用外部程序做事"的步骤，都要在**自己的进程里复核产物**，不能信退出码。

## H. 算法与流程类

### D1. 黑背景 + 掩码：COLMAP 与 3DGS 的“掩码用法”不一样
- **问题**：黑背景图喂 COLMAP 效果最好（背景不产生特征），但训练时如果也让黑背景参与损失，
  模型会把背景学成一堆黑色高斯，前景质量被拖累。
- **解法**：
  - COLMAP：优先用 `--ImageReader.mask_path` 忽略背景；不支持时用纯黑图兜底（等价效果）。
  - 训练：掩码 PNG 同步到去畸变图同名下，**前 25% 迭代只在掩码内算 L1**，之后放开全图。
- **可调**：`train.mask_loss_until`（默认 0.25）。

### D2. `image_undistorter` 会把掩码一起做几何变换
- **问题**：直接把它指向 `02_masks` 会得到“变换后的掩码”，和去畸变图对不上；
  而且它的掩码语义是“0 表示忽略”。
- **解法**：喂给 undistorter 的一律是**全白掩码**（不忽略任何像素）；
  原掩码在准备阶段按 `name_map`（原名 → 去畸变名）映射，训练时按需缩放。
  见 `gsdata/colmap_io.py: prepare_undistorted()` 与 `stages/train.py: _sync_masks()`。

### D3. 密度控制的阈值必须按场景尺度归一化
- **问题**：官方 3DGS 用固定阈值（如 `> 0.01`）判断“高斯是否太小”，对大小不同的场景会失效。
- **解法**：`trainers/gsplat_trainer.py` 用相机中心平均距离估出 `scene_extent`，
  阈值取 `0.01 * scene_extent` / `0.5 * scene_extent`。

### D4. 密度控制改变张量形状后，优化器状态会失效
- **问题**：复制/裁剪高斯后，Adam 的动量缓存形状不匹配，轻则报错重则训练退化。
- **解法**：一旦高斯数量变化就**整体重建优化器与调度器**（`make_optimizers()`），
  与官方实现一致；不要试图 `clear()` 状态。

### D5. 不透明度没有任何上升压力 → 高斯“飘”在空中
- **解法**：每 3000 步把 logit 不透明度夹回 `0.1` 上限（官方做法），
  并在裁剪条件里加入“屏幕尺度 > 0.5*scene_extent”的超大高斯。

### D6. 导出 GLB：3DGS 的 PLY 不是带面网格
- **问题**：PLY 里只有高斯参数，没有三角形，常规 glTF 转换器会失败或产出垃圾。
- **解法**：我们的 `glb_points` 用 glTF `POINTS` 图元 + 顶点色（`KHR_materials_unlit`），
  任何 glTF 查看器都能打开；需要真网格（带三角面）时是另一条路线（SuGaR / 2DGS），
  已在架构里留作后续增强阶段。
- **SPZ**：更专业的压缩格式，但依赖第三方 `spz` 包；未安装时自动跳过并提示，不阻塞主流程。

### G53. AbsGS 的 `absgrad` 实测**没有收益**（且我前两次实验都是无效的）

### G54. 查看器"全黑"的真凶：WebGL1 的 `drawElements` 不接受 `UNSIGNED_INT`
用户反馈"查看器全黑"。根因由用户提供的 Edge 控制台一行定位：

```
GL INVALID_ENUM @ gl.drawElements(4, 222885, 5125(0x1405), 0)
                                             ^^^^ UNSIGNED_INT
```

**WebGL1 的 `drawElements` 只接受 `UNSIGNED_BYTE` / `UNSIGNED_SHORT`**；
要用 32 位索引必须**显式启用 `OES_element_index_uint` 扩展**。
我们无条件传了 `UNSIGNED_INT` ⇒ `INVALID_ENUM` ⇒ **一个图元都不画**，
而且**没有任何异常或提示**（错误只留在 GL 上下文里，直到有人 `getError()`）。
我们的网格普遍 3~4 万顶点（超过 `UNSIGNED_SHORT` 的 65535 上限），所以**几乎每个带面的模型都黑屏**；
点云走 `drawArrays`，因此一直正常 —— 与用户"应该是实体模型，这只有点云"的现象吻合。

**为什么连续几轮都查不出来（最重要的教训）**：
我的 Node mock **没有模拟这条 WebGL 约束**，而且**用的是我自己编的常量值**，
所以本地永远"通过"。加 `debug()`、GL 溯源器、常量校验、pname 校验都没用 ——
**模拟不够真，测出来的"通过"是假的**。
修法：mock 改用**真实 WebGL1 常量号**，并实现该约束（含 `getExtension`），
于是"用了非法索引类型"会像浏览器一样报错。

**修法（产品侧）**：`createRenderer` 探测扩展；`makeMesh` 按顶点数选类型
（≤65535 用 `UNSIGNED_SHORT`，否则 `UNSIGNED_INT` 并转换索引数组）；线框缓冲同类型；
无扩展且超限时**明确报错**（说明 65535 上限、扩展名、两个解决办法），不再静默黑屏。

### G55. 万向锁的真实症状是"**转不过顶/底**"，不是 NaN —— 最终用四元数解决
用户第三次反馈"还是有万向锁"。我前两次的"修复"都没解决**主观**问题：
1) 最初 `pitch` 硬夹 ±1.5 rad(±86°) ⇒ 竖直方向根本转不过去；
2) 改成 ±(π/2−ε) + `lookAt` 共线兜底 ⇒ **数值**安全了（0 个 NaN），
   但**仍然转不过顶/底**。我当时宣称"万向锁已修"是**错的** —— 我只消掉了 NaN，没消掉夹取。
3) 现在改成**四元数累积旋转**（用户建议），不再有会退化的 pitch 自由度。

实现要点：**增量旋转**而不是绝对 yaw/pitch —— 水平拖动绕**世界 Y 轴**（轨道相机习惯），
竖直拖动绕**相机当前右轴**（任意朝向下"向上拖就是向上转"，过天顶后局部右轴随之翻转、旋转自然接续）；
视图矩阵由四元数**直接构造正交基**（`m4viewFromQuat`），连 `lookAt` 的退化兜底都不再需要。

**验证判据也踩了坑**：我第一版探针断言"y 先升到峰值再回落"，在大幅连续旋转下会失败，
因为 y 序列本来就来回穿越两极（实测 `0.89 → −0.59 → … → 1.00 → … → −0.98`）。
正确判据是**"能否同时到达两个极点"**（旧实现会停在一个极点附近）。
实测：y 范围 **−1.000 ~ 0.999**、62 次 uMVP 采样 **0 个 NaN** ⇒ 可自由翻越。

### G58. "还有万向锁"的**真正机理**：不是 NaN，是**拖动中途反向**（走了四次弯路）
用户反馈三次"还有万向锁"，我前三版都没解决。**根因不是数值奇点，而是主观的"推回"** ——
持续朝同一方向拖动时，相机在某个位置**反向**，手感就是"转到某个方向就转不动了"。
四版实现与实测（`scripts/probe_camera_monotonic.mjs`，持续向下拖 2400px）：

| 版本 | 做法 | 实测结果 |
|---|---|---|
| 1 | 欧拉角 pitch 硬夹 ±1.5 rad | 竖直方向根本到不了顶/底 |
| 2 | 四元数 + 竖直绕**当前相机右轴**增量 | 数值安全（0 NaN），但过极点后右轴翻向 ⇒ **反向** |
| 3 | 四元数 **trackball**（增量） | y 仅 ±0.435 **来回震荡**，非极点区反向 **589 步**，到不了极点 |
| 4 | 四元数 **Arcball**（按按下点累积） | y 是**平滑正弦**（0.435→−0.435→0.435，周期≈840px），仍只扫 ±26° 圆环 |
| **5** | **yaw 绕固定世界 Y 轴（不限圈数）+ pitch 绕水平右轴（夹 ±90°）** | y **单调** 0.421→−0.502→−0.996→−1.000，**反向 0 步** ✅ |

**第 3/4 版为什么必然失败（几何原因，值得记住）**：
屏幕竖直位移对应的旋转轴 ⊥ 屏幕 up，于是相机绕**固定轴做圆锥运动**，只能扫出一个**圆环**，
**永远无法到达该轴以外的极点**。arcball 适合"抓着一个球随便转"，
但"看物体"的场景要求"向下拖就能看到底面"，两者目标不同。我照搬了 arcball 的公式却没核对它的几何行为。

**最终方案**把两件事解耦，语义清晰且无奇点：
- **水平拖动 = yaw**，绕**固定世界 Y 轴**（与相机朝向无关）⇒ 可无限圈转，无极点；
- **竖直拖动 = pitch**，绕**由 yaw 决定、恒水平**的右轴 ⇒ 上下扫到 ±90° 后夹住
  （这是"上下看"的自然边界，**不是卡死**：不会反向、不会回弹）。
两者用四元数相乘 `qcam = Qpitch ⊗ Qyaw`，因此没有欧拉角矩阵的退化。

**验签要点**：判据必须是**单调性**（"非极点区反向步数 = 0"），
我前两版探针用了"能否同时到达两极"和"相邻极值间弧长"，**大步长都能跳过反转区**，
所以把有缺陷的第 2 版也判成"通过"。**测试判据本身也要用已知有缺陷的实现验证能失败**，
否则就是"永远通过的假测试"。

### G59. 我写探针时反复犯的**同类错误**：判据被"夹取/边界"污染
三次都是同一个毛病 —— 判据里混入了与"卡不卡"无关的因素：
1) 用"y 变化方向的符号翻转次数"判断卡顿：竖直连拖会绕 12 圈，y 本来就**像正弦一样正负摆动**，
   ⇒ 必然得到 ≈12，与卡不卡无关。
2) 用"相邻极值间弧长应≈180°"：到了 ±90° 夹住后极值点密集出现，弧长≈0，属正常。
3) 用"最大/平均步长比"判断抖动：到达极点后步长归零，把**平均**拉低 ⇒ 比值虚高
   （实测 17.8，但**最大步长 2.29° 恰好等于输入量**，毫无抖动）。
⇒ 教训：**判据里出现"平均"时，先想清楚边界（夹住/静止）会不会把它拉偏**；
   优先用**与输入量直接比较**的判据（如"单步转角不应超过输入对应的 2.29°"）。

### G60. 相机符号错误：`pitch` 正负写反导致"向下拖反而升到天顶"
最终方案第一版里写成 `pitchAcc -= dy*SENS`，于是向下拖把相机转到了**天顶并夹住**。
实测序列直接暴露：`y = 0.449 → 0.990 → 1.000 → 1.000 …`（卡在 +1）。
改成 `+=` 后：`0.421 → −0.502 → −0.996 → −1.000`（正确落到天底）。
⇒ **方向类改动必须看数值序列，不能只看"有没有 NaN"** —— 符号错不会有任何异常。
